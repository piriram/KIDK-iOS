# Page 4 / 10 — 키득 (KIDK) 핵심 구현

## 01 REST API 통신 계층과 토큰 인터셉터 기반 인증 자동화

공통 응답 래퍼와 요청 가로채기 패턴으로 20개 엔드포인트 디코딩 로직 통일

**문제**
처음으로 실제 백엔드 서버와 통신하는 프로젝트에서 Spring + AWS 환경의 RESTful API 20개 엔드포인트를 구현해야 했다. 각 API의 응답 구조가 달라 계좌 조회는 배열을, 미션 생성은 단일 객체를, 에러는 상태 코드만 또는 메시지까지 반환하는 등 형식이 통일되지 않았다. 초기 3개 API 구현에 각각 평균 2시간이 걸렸으며, 매번 Codable 구조체를 새로 정의하고 에러 케이스를 if-else로 처리하다 보니 20개를 단순 계산해도 40시간이 예상되었다. 동일한 401 상태 코드라도 토큰 만료와 권한 부족을 구분해야 했고, 각 ViewModel에서 이 차이를 처리하려니 조건문이 중복되어 에러 처리 일관성이 없었다. 사용자는 Firebase로 로그인하지만 백엔드는 자체 JWT를 발급했고, Firebase Token으로 Access Token과 Refresh Token을 받은 뒤 모든 요청에 Access Token을 헤더에 첨부해야 했으며, 로그아웃과 토큰 갱신 같은 일부 API는 Refresh Token을 사용해야 했다.

**접근**
백엔드 팀과 협의하여 모든 API 응답을 ApiResponse<T> 공통 래퍼로 통일했다. 성공 시 success: true와 data: T를, 실패 시 success: false와 error: {code, message}를 반환하도록 하여 NetworkService에서 이 포맷 기준으로 디코딩하고, 성공 응답이면 data 필드를 추출해 반환하며 실패 응답이면 HTTP 상태 코드와 에러 코드를 함께 분석하여 NetworkError enum으로 매핑했다. 401은 unauthorized(code, message)로, 500번대는 serverError(statusCode, code, message)로 변환하여 ViewModel이 Observable<Result<T, NetworkError>>만 구독하면 되도록 했다. 표준화 후 신규 API 구현은 평균 20분으로 단축되어 20개 엔드포인트를 40시간이 아닌 7시간에 완성했다. RequestInterceptor 패턴으로 요청 전송 직전 adapt 메서드에서 헤더를 자동 추가했다. requiresAuth가 true인 엔드포인트 중 usesRefreshToken이 true면 Refresh-Token 헤더에, false면 Authorization 헤더에 Bearer 방식으로 Access Token을 실어 Repository가 토큰 타입을 신경 쓰지 않게 했다. TokenManager는 Keychain에서 요청 직전에 토큰을 읽어 항상 최신값을 사용했다.

**결과**
디코딩 실패율이 초기 15%에서 0.5% 미만으로 감소했고, 에러 원인 파악 시간이 평균 30분에서 5분으로 단축되었다. API 1개당 개발 시간이 2시간에서 20분으로 줄어들어 전체 개발 기간이 85% 단축되었으며, 이를 통해 백엔드 API 20개를 1주일 만에 완성하고 남은 시간을 UI 개선에 투자할 수 있었다. 에러 코드가 로그에 명확히 남아 백엔드 협업 시 소통이 빨라졌으며, 20개 엔드포인트 모두 동일한 에러 핸들링 로직을 공유하여 각 화면에서 중복 코드를 작성할 필요가 없어졌다. 엔드포인트 정의만으로 인증 방식이 자동 결정되어 토큰 타입 실수를 방지했고, HTTP 상태 코드와 백엔드 에러 코드를 함께 매핑하여 상황별 UI 분기가 가능해졌다.

## 02 Keychain 기반 토큰 보안 저장

**문제**
초기에는 Access Token과 Refresh Token을 UserDefaults에 저장했다. 자동 로그인 기능을 테스트하는 동안에는 문제가 없어 보였고, 앱을 종료하고 다시 열어도 토큰이 유지되어 사용자가 로그인 화면을 거치지 않고 메인 화면으로 진입했다. 문제는 보안 검토 과정에서 드러났다. UserDefaults는 평문으로 저장되어 탈옥된 기기나 백업 파일에서 데이터를 읽을 수 있었고, Access Token이 노출되면 해당 사용자로 위장한 API 호출이, Refresh Token까지 노출되면 무한정 토큰 갱신이 가능했다. KIDK는 아동의 용돈 데이터를 다루므로 토큰 탈취는 개인정보 유출로 직결되었다.

**접근**
시스템 레벨 암호화 저장소인 Keychain을 도입하여 토큰을 보관했다. 보안 API를 래핑한 클래스를 만들고 Access Token과 Refresh Token을 구분하여 저장했으며, 저장 시도 시 이미 존재하는 항목은 자동으로 업데이트하도록 했다. 저장소 인터페이스를 분리하여 테스트 환경에서는 실제 보안 저장소 대신 임시 메모리를 사용하도록 했다. 로그아웃 기능은 두 토큰을 모두 삭제하는 단일 메서드로 구현했으며, 서버 요청 실패 여부와 관계없이 로컬 데이터는 항상 정리되도록 보장했다.

**결과**
Keychain 도입으로 토큰 탈취 위험이 제거되었다. UserDefaults 사용 시 백업 파일에서 평문 토큰을 추출할 수 있었으나, Keychain 적용 후 암호화된 저장소로 보호되어 동일한 공격 방법이 차단되었다. 탈옥 기기에서도 추가 공격 없이는 토큰에 접근할 수 없게 되었고, 아동 용돈 데이터를 다루는 앱의 보안 요구사항을 충족했다. 저장소 추상화를 통해 다른 민감 데이터도 동일한 보안 수준으로 보호할 수 있는 기반이 마련되었다.

## 03 Firebase-백엔드 이중 인증 흐름 통합

비동기 체이닝으로 토큰 교환 2단계 로그인 순차 처리

**문제**
Firebase Authentication과 백엔드 자체 JWT를 모두 사용하는 인증 구조에서, 사용자는 Firebase로 로그인하지만 실제 API 통신에는 백엔드가 발급한 Access Token과 Refresh Token이 필요했다. Firebase 로그인만 구현하면 백엔드 API를 호출할 수 없고, 백엔드 로그인만 구현하면 Firebase의 보안 기능을 활용할 수 없어 두 시스템을 연결하는 토큰 교환 흐름이 필요했다. 먼저 Firebase에 로그인해 ID Token과 UID를 받고, 이를 백엔드에 보내 JWT를 교환받은 뒤 Keychain에 저장하는 순차적 실행이 필요했으며, 각 단계가 실패하면 다음 단계로 진행할 수 없고 Firebase 에러인지 백엔드 에러인지 구분해 사용자에게 알려야 했다.

**접근**
Firebase의 비동기 API를 RxSwift 스트림으로 변환하여 다른 비동기 작업과 조합할 수 있도록 했다. 로그인 성공 시 ID Token과 UID를 가져와 전달하고, 에러 발생 시 RxSwift 에러 처리 체인으로 전파했다. Firebase 로그인과 백엔드 로그인을 순차적으로 연결하여, Firebase 로그인이 성공하면 그 결과로 백엔드 로그인을 호출하는 2단계 흐름을 구성했다. 백엔드 응답을 변환하여 성공 시 사용자 정보를 방출하고 실패 시 에러를 전파했으며, 모든 단계가 성공하면 사용자 정보 저장과 최초 로그인 플래그 설정을 수행했다. 자동 로그인 상태는 별도 변수로 관리하여 앱 실행 시 저장된 설정을 불러왔고, 로그인 성공 시 자동 로그인이 활성화되어 있으면 이메일을 저장하여 다음 실행 시 입력 필드에 자동으로 채워지도록 했다.

**결과**
비동기 흐름을 순차적으로 연결하여 Firebase 로그인 결과를 기다렸다가 백엔드 로그인을 호출하는 로직을 명확하게 표현했고, 콜백 중첩 없이 가독성을 확보했다. 로그인 버튼 탭, 이메일 입력, 비밀번호 입력을 하나의 스트림으로 통합하여 처리했으며, 각 단계에서 에러 발생 시 체인이 중단되고 사용자에게 적절한 메시지를 표시했다. 저장된 이메일을 자동으로 채워줘 사용자가 비밀번호만 입력하면 되도록 했고, 두 인증 시스템을 투명하게 연결하여 사용자는 하나의 로그인 절차만 인지하게 되었다.

## 04 Vision 프레임워크 기반 영수증 OCR 자동 파싱

키워드 기반 컨텍스트 분석과 자동 입력 후 검증 워크플로우로 입력 시간 75% 단축

**문제**
아이들이 편의점에서 과자를 사고 받은 영수증의 금액을 기록할 때 매번 금액과 상호명을 직접 입력하는 것이 번거로웠고, 초등학생 사용자는 숫자 입력 실수가 많아 입력 과정이 길면 앱 사용을 포기했다. OCR로 영수증을 스캔해 자동으로 거래 내역을 생성하면 입력 시간을 줄일 수 있지만, Vision 프레임워크는 영수증이 구겨지거나 빛 반사로 일부가 안 보이는 경우 인식 정확도가 떨어졌다. 금액을 잘못 읽으면 1,000원을 10,000원으로 기록할 수 있어 아이의 잔액을 크게 왜곡하므로, OCR 결과를 어디까지 자동화하고 어디서 사용자 확인을 요구할지 설계가 필요했다.

**접근**
Vision 프레임워크의 텍스트 인식을 accurate 모드로 설정하여 처리 시간이 0.5초 늘지만 소수점과 쉼표 인식 정확도를 높였고, 한글과 영어를 모두 지원하도록 설정하여 "CU", "합계" 같은 혼합 텍스트를 처리했다. Document Camera를 우선 사용하여 자동으로 영수증 경계를 감지하고 조명을 보정하여 배경 없이 영수증만 추출했다. 영수증에서 결제 금액을 추출할 때 "합계", "총액", "결제금액", "total" 같은 키워드를 먼저 찾고 그 주변 3줄 이내의 숫자를 금액으로 인식했으며, 키워드를 못 찾으면 가장 큰 숫자를 반환하는 방식으로 정확도를 85%에서 95%로 향상시켰다. 상호명은 첫 5줄 중 가장 긴 줄을 선택하되 2글자 미만이나 30글자 초과는 제외하여 전화번호나 주소가 잘못 인식되는 것을 방지했다. OCR 결과를 입력 필드에 자동으로 채우되 편집 가능한 상태로 남겨두어 사용자가 정확하면 바로 저장하고 틀렸으면 수정 후 저장하도록 했으며, 모든 필드가 입력되어야 저장 버튼이 활성화되도록 검증 로직을 추가했다.

**결과**
평균 입력 시간이 수동 입력 30초에서 자동 입력 후 확인 8초로 75% 단축되었고, 오류율은 수동 입력 5%에서 1%로 감소했다. Document Camera 사용으로 텍스트 인식률이 75%에서 95%로 향상되었으며, 키워드 기반 파싱과 휴리스틱 조합으로 다양한 영수증 포맷에 대응했다. 자동 입력 후 확인 워크플로우로 기술의 한계를 인정하면서도 사용자 편의성을 확보했고, 불완전한 데이터가 저장되는 것을 방지하여 잔액 정확성을 유지했다. 아이들이 꾸준히 거래를 기록하도록 유도하여 앱 사용 지속률이 향상되었다.

## 03 Watch-iPhone 양방향 동기화 충돌 해결
타임스탬프 기반 병합 전략으로 데이터 손실 없는 양방향 동기화 구현

**문제**
Watch와 iPhone이 오프라인 상태에서 각각 동일한 서핑 기록을 수정한 뒤 재연결되면, 두 디바이스의 데이터가 충돌하여 일관성이 깨지는 문제가 있었다. 단순히 나중에 수정한 데이터만 유지하면 먼저 수정한 쪽의 변경 사항이 손실되고, 양쪽 수정 사항을 모두 보존하려 하면 동일한 기록이 중복 생성되었다. 특히 한쪽에서 기록을 삭제하고 다른 쪽에서 수정한 경우, 삭제 정보가 전파되지 않아 이미 삭제된 기록이 다시 나타나는 현상도 발생했다. WatchConnectivity의 비동기 특성상 두 디바이스가 언제 동기화될지 예측할 수 없어, 충돌 해결 전략 없이는 데이터 무결성을 보장할 수 없었다.

**접근**
수정 시각 기준 "최신 우선 병합 + 삭제 전파" 전략을 채택했다. 각 기록에 마지막 수정 시각(lastModifiedAt)과 디바이스 식별자(deviceID) 필드를 추가하여 어느 디바이스에서 언제 수정했는지 추적했다. 삭제는 실제로 지우지 않고 삭제 표시(isDeleted 플래그)만 남기는 방식으로 처리해, 삭제 정보가 다른 디바이스로 전달되어 양쪽에서 모두 삭제되도록 했다. 동일한 수정 시각으로 충돌할 드문 경우를 대비해 디바이스 식별자를 사전순 비교하여 어느 디바이스에서 병합하든 항상 동일한 결과를 보장했다. WatchConnectivity로 양방향 통신을 구현하되, 전체 데이터가 아닌 변경된 필드만 전송하는 증분 업데이트를 적용해 메시지 크기를 70% 감소시켰다. 충돌 해결 로직은 별도 클래스로 분리하여 삭제 우선 → 최신 수정 시각 우선 → 디바이스 식별자 사전순 선택 규칙을 순차 적용했고, 여러 기록을 하나의 메시지로 묶는 배치 동기화와 실패 시 자동 재시도 로직도 추가했다.

**결과**
Watch와 iPhone에서 동시 수정이 발생해도 데이터 손실이나 중복 없이 일관된 기록이 유지되었고, 동기화 충돌로 인한 크래시가 0건으로 감소했다. 증분 업데이트로 메시지 크기가 평균 70% 감소하여 배터리 소모가 줄었고, 배치 동기화는 메시지 전송 횟수를 60% 감소시켜 블루투스 부하를 낮췄다. TestFlight 베타 테스터로부터 "양쪽 디바이스에서 항상 동일한 기록이 보인다"는 평가를 받았으며, 데이터 불일치로 인한 사용자 문의가 사라졌다.

## 04 지역별 차트 조회 성능 개선
LRU 메모리 캐시와 예측 알고리즘으로 조회 속도 단축 및 비용 절감

**문제**
서퍼들이 당일 최적의 서핑 스팟을 찾기 위해 3-5개 지역을 연속으로 조회하는 과정에서, 매번 Firestore에 새로운 요청이 발생했다. 각 요청은 평균 1.2초가 소요되어 5개 지역 비교 시 총 6초의 대기 시간이 발생했고, 이미 조회한 지역을 재선택해도 동일한 데이터를 다시 요청하는 구조였다. 아직 마케팅을 시작하지 않은 상태에서 서핑 시즌(6-9월) 사용자 수를 500명으로 예측했을 때, 1인당 일평균 20회 지역 조회를 가정하면 월 30만 읽기가 발생한다. Firestore는 월 5만 읽기까지 무료이지만 이후 100만 읽기당 과금되는 구조이므로, 캐싱 없이는 시즌 첫 달부터 비용이 발생할 것으로 예상되었다. 반복 조회로 인한 대기 시간은 사용자가 여러 지역을 빠르게 비교하는 워크플로우를 방해하는 요소라고 생각되었다.

**접근**
이미 조회한 데이터를 재사용하는 메모리 캐시와 다음 조회를 예측하는 prefetch를 결합했다. 캐시는 NSCache 기반 LRU 방식으로 구현하여 최근에 사용한 데이터를 우선 보존하고, 메모리 부족 시 시스템이 자동으로 오래된 항목을 제거하도록 했다. 세션당 평균 7개 지역 조회 패턴을 고려해 최대 10개 항목을 캐싱하며, 차트당 50KB로 총 500KB 메모리만 사용한다. Prefetch 알고리즘은 현재 선택한 지역과 지리적으로 인접한 스팟과 과거 조회 이력을 조합하여 다음 조회 가능성이 높은 3개 지역을 백그라운드에서 미리 로드했다. ChartCacheManager 클래스로 캐시 로직을 캡슐화하고 접근 순서 배열로 LRU 정책을 명시적으로 추적했다. 캐시된 데이터를 즉시 표시하면서도 백그라운드에서 최신 데이터를 조용히 가져와 해시값 비교 후 변경이 있을 때만 UI를 업데이트하는 stale-while-revalidate 패턴을 적용했다.

**결과**
캐시 히트율 70%를 달성하여 불필요한 네트워크 요청이 50% 감소했고, 이는 Firebase 월 비용 35% 절감으로 이어졌다. 예상했던 월 30만 읽기 중 15만 건이 캐시로 처리되어 과금 없이 서비스를 운영중이다. 캐시 히트 시 차트 표시 시간이 1.2초에서 0.3초로 75% 단축되었고, prefetch로 다음 지역 선택 시 즉시 표시 비율이 60%에 달했다. 여러 지역을 빠르게 비교하는 워크플로우가 개선되면서 평균 세션 시간이 15% 증가했다.

## 06 Live Activities와 Dynamic Island 기반 실시간 세션 모니터링

잠금 화면 통합으로 앱 실행 없는 세션 상태 확인 구현

**문제**
서핑 세션 진행 중 사용자는 iPhone을 방수 케이스에 넣어 해변에 두고 바다로 들어가므로, 세션 진행 상황을 확인하려면 젖은 손으로 iPhone을 꺼내 잠금 해제 후 앱을 열어야 했다. 전통적으로 앱은 사용자가 명시적으로 열어야만 정보를 볼 수 있어, 실시간으로 진행되는 활동을 추적하는 앱에게는 치명적인 제약이었다. 사용자는 "지금 몇 분째 서핑 중인지", "몇 번의 파도를 탔는지" 같은 정보를 빠르게 확인하고 싶어 했지만, 앱을 열기까지의 마찰이 너무 컸고, 서핑처럼 시간에 민감한 활동에서는 지속적인 상태 확인을 위해 이 마찰을 줄이는 것이 핵심 사용자 경험 문제였다.

**접근**
iOS 16의 Live Activities와 Dynamic Island를 ActivityKit 프레임워크로 구현하여 잠금 화면과 노치 영역에서 실시간 세션 정보를 표시했다. ActivityAttributes 프로토콜로 고정 정보(시작 시간, 해변 이름)와 동적 정보(경과 시간, 라이딩 횟수, 평균 심박수)를 분리하여 업데이트 효율성을 높였고, 경과 시간은 1분 간격, 라이딩 횟수는 즉시, 심박수는 10초 간격으로 업데이트하여 정보 신선도와 배터리 효율의 균형을 맞췄다. Widget Extension에서 SwiftUI로 Dynamic Island의 축소/확장/최소 상태별 레이아웃을 구성하고, 라이딩 횟수 증가 시 페이드 애니메이션과 심박수 임계값 초과 시 펄스 애니메이션을 적용하여 변화를 즉시 인지하게 했다. 배터리 최적화를 위해 세션 초반 1분 간격, 30분 후 5분 간격, 1시간 후 10분 간격으로 업데이트 빈도를 동적 조정했고, Live Activity 탭 시 딥링크로 세션 상세 화면 이동, 길게 누르면 조기 종료 옵션을 제공했다.

**결과**
사용자가 세션 상태를 확인하는 빈도가 약 5배 증가했고, 앱을 열지 않고도 잠금 화면에서 즉시 확인 가능해져 사용자 참여도가 높아졌다. iPhone을 방수 케이스에서 꺼내는 빈도가 감소하여 물 손상 위험이 낮아졌고, 라이딩 횟수 실시간 확인으로 "한 번 더 타자"는 동기 부여 효과가 발생했다. 업데이트 빈도 동적 조정으로 배터리 수명이 약 25% 연장되었으며, Dynamic Island 지원으로 앱이 최신 iOS 기능을 적극 활용한다는 긍정적 이미지를 형성했다. 사용자는 앱을 열지 않고도 필요한 정보를 즉시 확인할 수 있게 되어, 기술이 흐름을 방해하지 않고 자연스럽게 통합되었다.

## 07 목업 데이터 기반 개발 전략

외부 API 중단 상황에서 개발 연속성 확보

**문제**
2025년 9월 26일 국가정보자원관리원 화재로 기상청 공공데이터포털 API가 약 2주간 중단되었다. DoSurf는 실시간 파도, 바람, 기상 데이터에 전적으로 의존하는 서비스로, API 중단 시 신규 기능 개발과 테스트가 불가능해졌다. 차트 렌더링, 날씨 분류 로직, 데이터 저장 등 핵심 기능 개발이 모두 멈춰 2주 이상의 개발 일정 지연이 불가피한 상황이었다.

**접근**
API 중단 이전 수집한 실제 응답 구조를 분석하여 Firestore에 목업 데이터 세트를 구축했다. 프로토콜 기반 추상화 설계로 앱의 비즈니스 로직 계층이 데이터 출처를 인지하지 못하도록 격리했다. 데이터 접근 인터페이스를 프로토콜로 정의하고 실제 구현체가 이를 준수하도록 하여, ViewModel과 UseCase가 실제 API인지 목업 데이터인지 알 수 없게 만들었다. DTO는 기상청 API의 모든 필드를 Optional로 정의하여 실제 응답의 가변성을 반영했고, RxSwift 기반 비동기 처리 구조를 그대로 유지했다. 목업 데이터는 강릉, 포항, 제주, 부산 4개 지역 11개 해변의 3시간 간격 72시간 예보를 Firestore에 저장하여 실제 프로덕션 환경과 동일한 쿼리 방식을 보장했다.

**결과**
API 중단 기간 동안 개발을 멈추지 않고 차트 렌더링, 날씨 타입 분류, 서핑 기록 저장 등 핵심 기능을 완성했다. API 복구 후 데이터 수집 로직만 재개하면 되었고, 앱 코드는 단 한 줄의 수정 없이 실제 데이터로 전환되었다. 계층 간 의존성 주입을 통한 격리 설계가 데이터 소스를 교체할 때 기존 코드 수정 없이 전환 가능하게 만들었으며, 2주간의 잠재적 일정 지연을 완전히 회피하여 계획된 배포 일정을 준수했다. 외부 API 의존성을 추상화하는 설계의 중요성을 검증했고, 향후 예상치 못한 외부 시스템 장애 상황에서도 개발을 지속할 수 있는 대응 능력을 확보했다.

## 01 의료 안전 기준을 반영한 우선순위 기반 메시지 판단 시스템
피임약은 하루만 건너뛰어도 효과가 떨어지고, 이틀 이상 놓치면 위험이 급격히 커진다. 앱은 사용자의 복용 상태에 따라 “오늘 복용”, “어제 것과 함께 2알 복용”처럼 상황별 메시지를 정확히 보여줘야 했고, 연속 미복용 일수, 전날 복용 여부, 예정 시각 대비 지연 시간(24~36시간, 36~48시간 구간) 등 여러 조건을 동시에 고려해야 했다. 초기 구현은 모든 조건을 하나의 if-else로 처리했지만, “2일 연속 미복용”과 “2시간 지연”이 동시에 발생할 때 어떤 메시지를 우선해야 하는지 코드에 명시되지 않았고, 의료 지침이 추가될 때마다 전체 조건문을 다시 검토해야 했다. 이를 해결하기 위해 의료 위험도에 따라 숫자 우선순위를 부여하는 독립 규칙 객체로 재설계했다. 예를 들어 연속 미복용 규칙은 priority 100, 2알 복용 가능 규칙은 priority 200처럼 위험도가 높을수록 낮은 번호를 받는다. 엔진은 규칙들을 우선순위로 정렬한 뒤 각 규칙이 현재 상황에 해당하는지 먼저 평가하고, 첫 번째로 매칭된 규칙이 메시지를 결정한다. 그래서 위험한 상황이 덜 위험한 상황보다 먼저 처리된다. 이 구조에서는 “이틀 연속 미복용”일 때 긴급 경고가 우선 표시되고, 단순 2시간 지연은 완화된 안내로 처리된다. 규칙이 서로 독립되어 있어 새로운 기준(예: 3일 이상 미복용 시 즉시 진료 권장)을 추가할 때도 priority 50의 규칙 클래스 하나만 만들면 되며 기존 코드는 수정하지 않는다. 또한 규칙을 클래스 단위로 분리해 “어제 복용 안 함 + 오늘 예정 시각 통과” 같은 시나리오를 단위 테스트로 재현할 수 있었고, 우선순위가 의료 지침과 일치하는지 검증 가능했다. 이 설계는 코드를 정리하는 수준을 넘어 의료 로직의 정확성과 안전성을 보장하는 핵심 장치가 되었다.

## 02 앱과 위젯 간 실시간 데이터 동기화 구조 설계
iOS에서 홈 화면 위젯은 메인 앱과 완전히 다른 프로세스에서 실행된다. 마치 두 개의 독립된 프로그램처럼 작동하기 때문에, 사용자가 앱에서 “오늘 약을 복용했습니다”를 누르면 위젯은 여전히 “아직 복용하지 않았습니다”를 표시하는 문제가 발생한다. 반대로 위젯에서 기록한 정보가 앱에 반영되지 않을 수도 있다.

초기 설계에서는 앱과 위젯이 각각 독립된 데이터베이스 파일을 사용했고, 데이터를 옮기는 작업을 수동으로 처리해야 했다. 이는 복용 기록이 누락되거나 중복 저장되는 문제로 이어졌고, 특히 복용 시간 초과 알림처럼 정확한 상태 판단이 필요한 기능에서 치명적이었다.

이 문제를 근본적으로 해결하기 위해 App Groups 공유 저장소 기능을 활용해 앱과 위젯이 하나의 데이터베이스 파일을 동시에 바라보도록 구조를 재설계했다. 단순히 파일 경로만 바꾼 것이 아니라, 여러 프로세스에서 동시에 데이터를 수정할 때 발생할 수 있는 충돌을 방지하기 위해 자동 병합 정책을 적용했다. 앱에서 복용 기록을 추가하는 동시에 위젯이 통계를 계산하더라도 변경사항이 자동으로 통합되어 데이터 손실이 발생하지 않도록 했다.

또한 데이터베이스 구조가 바뀔 때 기존 사용자 데이터를 보존하면서 자동으로 전환되도록 라이트 마이그레이션을 설정했다. 이는 앱 업데이트 시 데이터 불러오기 오류를 예방하고 사용자 경험을 끊김 없이 유지하기 위한 조치였다.

결과적으로 사용자가 앱에서 복용 버튼을 누르는 순간 위젯도 즉시 “복용 완료” 상태로 업데이트되고, 위젯을 터치해 기록한 정보도 앱 대시보드에 실시간으로 반영된다. 두 화면의 정보가 항상 정확히 일치하며 개발자는 동기화 코드를 따로 작성할 필요가 없다. 프로세스 간 격리라는 운영체제 제약을 공유 저장소와 자동 병합이라는 기법으로 극복해 복용 기록의 정확성과 신뢰성을 확보한 것이 핵심 성과다.

## 03 Diffable Data Source 기반의 단일 셀 갱신 구조 확보
캘린더 화면은 특정 날짜의 복용 상태가 변경될 때 전체 컬렉션을 다시 그리는 방식으로 처리되어, 불필요한 렌더링과 부자연스러운 화면 전환이 발생하는 문제가 있었다. 이러한 구조를 개선하기 위해 날짜 정보를 독립된 항목으로 모델링하고, 변경된 항목만 새 스냅샷으로 재구성하는 Diffable Data Source 기반 구조로 전환하였다.

Diffable Data Source는 항목 식별자를 기준으로 변경 대상을 안전하게 추적하며, 전체 레이아웃을 유지한 채 필요한 셀만 갱신할 수 있는 특성이 있다. 이를 활용해 변경된 날짜 셀만 정확하게 업데이트하도록 구성함으로써, 콘텐츠 전환이 자연스럽고 데이터 흐름과 뷰 상태가 일관되게 유지되는 구조를 확보하였다.

또한 날짜별 갱신을 위한 전용 업데이트 경로를 마련하여, 도메인 계층에서는 변경된 날짜 정보를 전달하고 뷰 계층에서는 해당 항목을 찾아 스냅샷을 갱신하는 방식으로 역할을 분리하였다. 이 방식을 통해 다양한 사용자 흐름에서 동일한 갱신 절차를 재사용할 수 있었고, 화면의 안정성과 유지보수성이 함께 강화되었다.


  04 의료 규칙 기반 단위 테스트

  문제

  피임약 복용 로직은 의학적 안전성과 직결되며, ±2시간 허용 범위, 1일 누락 시 2알 복용, 2일 연속 누락 시 추가 피임법 필요 등 복약 지도 규칙을 정확히 반영해야 한다. 그러나 초기 개발 중 "어제 09:00에 예정이었는데 오늘 06:30에 복용하면 '너무 일찍 복용함' 메시지가 나와야 하는데 '한 알 더 필요해요'가 나온다"는 버그를 발견했고, 이는 EarlyTakingRule과 YesterdayMissedRule의 우선순위 충돌 때문이었다. 또한 "scheduled + 정확히 2시간" 같은 경계값 검증을 위해 Date()를 직접 사용하면 테스트 실행 시각에 따라 결과가 달라져 재현이 불가능했다. 특히 타임존 변경(GMT → KST)이나 자정 경계 케이스를 테스트하려면 시스템 시간을 직접 조작해야 하는데, 이는 CI/CD 환경에서 불가능했다.

  접근

  시간 정보를 제공하는 기능을 TimeProvider 프로토콜로 분리하고, 프로덕션에서는 RealTimeProvider(Date()와 Calendar.current 반환), 테스트에서는 MockTimeProvider(now, calendar, timeZone을 원하는 값으로 고정)를 주입하도록 구성했다. 모든 UseCase와 Factory는 생성자에서 TimeProvider를 받아 now 대신 timeProvider.now, Calendar.current 대신 timeProvider.calendar를 사용하도록 수정했다.

  피임약 복약 지도 규칙을 7개 카테고리로 분류하고 각 경계값을 검증하는 39개 단위 테스트를 작성했다:

  1. 복용 시간 규칙 (6개): scheduled ± 2시간 경계, 너무 이른 복용, 12시간 이상 지연
  2. 누락 복용 보상 (5개): 어제 missed + 오늘 미복용/1알/2알 복용 조합
  3. 연속 미복용 (4개): 1일/2일/3일+ 누락 시 메시지 강도 단계
  4. 사이클 전환 (6개): 21일차 → 휴약기, 휴약 7일 → 새 사이클
  5. 휴약기 처리 (4개): 휴약일 메시지, 휴약기 복용 시도
  6. 2알 복용 시나리오 (4개): 정상 상태에서 2알, 어제 누락 후 2알
  7. 우선순위 규칙 (10개): 여러 조건 동시 충족 시 올바른 메시지 반환

  예를 들어 "±2시간 경계값 검증"의 핵심 테스트는:
  func test_허용범위_경계_정시복용() {
      mockTimeProvider.now = "2024-01-10 10:59:00"  // scheduled + 1시간 59분

      mockTimeProvider.now = "2024-01-10 11:01:00"  // scheduled + 2시간 1분
      // ...
      XCTAssertEqual(status.medicalTiming, .delayed)  // 지연 복용
  }

                                         status: .missed)

                                     takenAt: "2024-01-10 09:10")

      let result = calculateMessageUseCase.execute(cycle: cycle, for: now)

  }

  결과

  테스트 커버리지가 48%에서 68%로 향상되었고, 우선순위 규칙 충돌로 인한 버그 3건을 발견해 수정했다. 특히 "어제 누락 + 오늘 이른 시각 복용" 시나리오에서 EarlyTakingRule이 YesterdayMissedRule보다 먼저 평가되어 "너무 일찍 복용함" 메시지가 나오는 문제를 발견했고, EarlyTakingRule에 yesterdayNotMissed 조건을 추가해 해결했다.

  연속 미복용 계산 로직에서도 버그를 발견했다. DB에 명시적으로 .missed 상태로 저장된 레코드를 시간 경과로만 판단하다 보니 "어제 09:00 missed + 오늘 06:30 복용"일 때 연속 미복용이 1일로 계산되어야 하는데 0일로 계산되었다. calculateConsecutiveMissedDays를 수정해 DB 상태를 우선 확인하고, 그 다음 시간 경과를 판단하도록 변경했다.

  TimeProvider 도입 전에는 경계값 버그를 발견하려면 실제 시각에 앱을 실행해봐야 했고(scheduled + 2시간을 테스트하려면 11:00까지 대기), 휴약기 전환을 검증하려면 21일을 기다려야 했다. 도입 후에는 모든 경계 케이스를 1초 만에 자동 검증할 수 있어 새로운 메시지 규칙 추가 시 회귀 테스트가 즉시 수행되고, 버그 수정 시간이 평균 30분에서 5분으로 단축되었다. 현재는 타임존 변경(해외 여행 시)과 일광절약시간 전환 케이스가 미검증 상태인데, 이를 추가하면 국제 사용자 지원 시 안전성을 높일 수 있을 것으로 기대한다.

# Page 10 / 10 — 프레임밋 (Frameet) 핵심 구현

## 01 Vision 기반 자동 누끼와 고해상도 합성
프레임밋의 핵심 구현 1번은 Vision/VisionKit의 VNGenerateForegroundInstanceMaskRequest로 전경(인물) 마스크를 만들고, Core Image의 CIBlendWithMask로 배경을 제거한 뒤, SwiftUI의 ImageRenderer로 고해상도 합성 결과를 만드는 파이프라인을 단일 ViewModel(DFEditViewModel) 안에 묶은 구조다. 팬이 올린 사진의 배경을 자동으로 걷어내고 곧바로 프레임 편집에 쓰려면 “자동 누끼(Vision) → SwiftUI 렌더 → 합성” 흐름이 끊기지 않아야 했고, 중간에 해상도 손실이 생기면 사용자 체감 품질이 급격히 떨어졌다. 그래서 누끼 결과와 브러시 보정 레이어, 프레임 합성 레이어를 모두 SwiftUI 캔버스에서 관리하고, 그 캔버스를 ImageRenderer로 그대로 비트맵화해 최종 결과를 만들어 품질 저하 없이 편집에서 저장까지 이어지도록 했다.

이 구조를 선택한 이유는 두 가지다. 첫째, Vision의 전경 마스크는 자동 누끼 품질의 출발점이기 때문에, 빠르게 안정적인 기본 상태를 제공해야 했다. 둘째, SwiftUI 캔버스를 비트맵으로 직접 추출하면 브러시 보정 이후에도 다운스케일 없이 고해상도를 유지할 수 있다. 일반적인 이미지 합성 흐름에서는 중간 단계에서 해상도가 줄거나, 편집 뷰와 저장 이미지 사이에 차이가 생기는 문제가 생긴다. ImageRenderer를 통해 “화면에 보이는 편집 상태” 자체를 고해상도로 추출하면 이 문제를 근본적으로 줄일 수 있다.

기술 선택은 기능 요구와 제약을 기준으로 명확히 나눴다. Vision/VisionKit은 VNGenerateForegroundInstanceMaskRequest로 전경 마스크를 생성해 자동 누끼의 기본 품질을 담당한다. Core Image는 CIBlendWithMask로 마스크를 적용해 배경 제거를 수행한다. SwiftUI ImageRenderer는 브러시 레이어, 마스크, 원본을 포함한 SwiftUI 뷰 전체를 고해상도로 비트맵화해 편집 결과와 저장 결과의 일치를 보장한다. 마지막으로 Vision 연산 이후 UI 업데이트는 Task @MainActor에서 수행해 메인 스레드 안전성을 확보했고, UI 프리즈나 크래시 없이 결과 이미지를 갱신하도록 구성했다.

처리 흐름은 DFEditViewModel에서 일관된 상태 전환으로 관리한다. 첫 단계는 SwiftUI 캔버스를 ImageRenderer로 캡처해 inputImage를 저장하는 것이다. 두 번째 단계는 Vision으로 마스크를 생성하고 Core Image로 배경을 제거해 resultImage를 업데이트하는 과정이다. 세 번째 단계는 필요할 때 maskImageList에 마스크를 push해 undo/redo가 가능한 히스토리를 유지하는 것이다. 마지막 단계는 미리보기나 적용 시 createResult에서 최종 합성 이미지를 반환해 저장 또는 공유 흐름으로 연결하는 것이다. 이 과정을 하나의 ViewModel에 묶어 편집 상태와 결과 생성이 분리되지 않도록 했다.

핵심 코드도 이 흐름을 그대로 반영한다. showMaskImage는 ImageRenderer로 캔버스를 캡처해 inputImage를 만들고 removeBackground를 호출해 자동 누끼를 실행한다. createMask는 VNImageRequestHandler와 VNGenerateForegroundInstanceMaskRequest로 전경 마스크를 생성하며, apply는 CIFilter.blendWithMask로 배경 제거를 수행한다. removeBackground는 Task @MainActor에서 마스크 생성과 합성을 수행해 resultImage를 갱신한다. createResult는 최종 합성 이미지를 만들어 미리보기와 저장 단계에서 동일한 결과를 사용하도록 했다. 이 구조 덕분에 편집 화면과 저장 이미지의 품질 차이가 줄고, 처리 경로가 하나로 통합되어 유지보수성이 높아졌다.

또한 수동 보정 경험을 고려해 마스크와 결과 이미지를 스택으로 관리했다. maskImageList와 indexOfMask를 통해 undo/redo를 구현해 사용자가 잘못된 스트로크를 빠르게 되돌릴 수 있고, 브러시/지우개 입력을 최소화하도록 했다. 내부 QA 기준으로 자동 누끼 도입 이후 수동 브러시 입력 횟수가 약 40퍼센트 감소했다. 이는 자동 누끼로 “그럴듯한 기본 상태”를 제공하고, 사용자는 부족한 부분만 보정하도록 UX를 재구성했기 때문이다. 또한 미리보기 토글을 분리해 누끼 상태 확인과 브러시 입력을 명확히 구분했고, 결과적으로 보정 작업 시간이 줄었다.

정리하면, Vision 기반 전경 마스크 생성과 Core Image 합성을 통해 자동 누끼의 품질을 확보하고, SwiftUI ImageRenderer로 편집 캔버스를 그대로 고해상도 비트맵화해 편집과 저장 사이의 품질 손실을 최소화했다. 모든 처리는 DFEditViewModel에 집중시켜 파이프라인을 단일화했고, @MainActor에서 UI 업데이트를 수행해 안정성을 유지했다. 이 구조는 자동 누끼의 품질, 편집 UX, 저장 결과의 일치라는 세 가지 요구를 동시에 만족시키는 구현이었다.


## 04 카메라 오버레이와 프레임 재사용 흐름
촬영 전에 최종 합성 결과를 확인할 수 있어야 “찍고 확인” 왕복이 줄어든다. 그래서 선택한 프레임을 카메라 미리보기 위에 실시간으로 오버레이하는 구조를 만들었다. 사용자는 프레임 안에 정확히 위치를 잡고 바로 셔터를 누를 수 있고, 결과가 예상과 다르면 촬영 전에 바로 수정할 수 있다. 이 흐름을 위해 프레임 선택, 카메라 진입, 촬영 및 수정이 하나의 상태 흐름으로 연결되도록 설계했다.

핵심은 선택된 프레임 ID를 전역 상태로 보관하는 것이다. FrameManager에 selectedFrame과 updateFrame을 두어 선택한 프레임이 카메라 화면과 수정 화면에 전달되도록 했다. 프레임 선택 화면에서 selectedFrame을 설정하고, 카메라 진입 시 CameraView가 이 ID로 Core Data의 프레임 이미지를 로드해 미리보기 위에 합성한다. 오버레이는 allowsHitTesting(false)로 설정해 카메라 제스처나 줌과 충돌하지 않도록 분리했다. 이 방식으로 사용자는 촬영 단계에서 프레임 위치를 즉시 확인할 수 있다.

프레임을 “템플릿”처럼 다시 찍고 수정하려면 이미지 한 장만 저장해서는 부족하다. 인물 누끼, 텍스트, 스티커, 위치, 스케일, 회전 같은 레이어 메타데이터까지 보존해야 동일한 상태로 재편집이 가능하다. 그래서 Core Data에 프레임 이미지를 저장할 뿐 아니라, 각 레이어를 Subject 엔티티로 저장해 원본 이미지, 마스크, 텍스트 스타일, 스티커, 좌표와 각도를 함께 기록했다. 이후 수정 화면에 진입하면 저장된 Subject를 SubjectImage로 변환해 레이어를 복원하고, 마지막에 선택한 레이어가 즉시 편집되도록 상태를 재구성했다.

구현은 Source/Model/FrameManager.swift, Source/View/ManageFrame/MFDetailView.swift, Source/View/Camera/CameraView.swift, Source/Model/DFModifyViewModel.swift에 분산되어 있다. MFDetailView에서 selectedFrame과 updateFrame을 지정하고, CameraView에서는 선택된 프레임을 FilteredCoreDataImageView로 오버레이한다. DFModifyViewModel에서는 ImageRenderer로 SwiftUI 합성 결과를 고해상도로 렌더링해 저장하고, 기존 레이어는 제거한 뒤 새 레이어 집합으로 갱신한다. 이 흐름 덕분에 촬영, 수정, 재촬영이 하나의 상태 흐름으로 이어지고, 사용자는 항상 동일한 프레임 컨텍스트에서 작업할 수 있다.
