## 01 의료 안전 기준을 반영한 메시지 우선순위 엔진

복용 상태에 따라 필요한 안내를 정확한 규칙으로 제공하는 구조

- **문제**
  복용을 하루 누락했을 때와 연속 누락했을 때 안내가 다르지만, 하나의 긴 조건문에 섞여 있어 어떤 상황이 더 위험한지 순서가 드러나지 않았다. 이틀 연속 누락과 2시간 지연이 동시에 발생하면 어떤 메시지를 우선할지 명시되지 않아 잘못된 안내 위험이 있었다.

- **접근**
  의료 가이드라인의 "위험도가 높은 상황을 먼저 안내" 원칙을 코드에 반영했다. 각 메시지 조건을 `MessageRule` 프로토콜을 따르는 독립 객체로 분리하고, `priority`(규칙 평가 순서를 정하는 정수로 낮은 값일수록 우선 평가)를 부여했다.
  `MessageRuleEngine`은 규칙을 우선순위로 정렬해 순차 평가하고 첫 매칭 메시지만 반환하도록 했으며, 예정 시각 대비 시간 차이를 단계화해 모든 규칙이 동일한 기준으로 시간을 계산하게 했다.

- **결과**
  위험도가 높은 상황이 항상 먼저 안내되어 누락·지연이 겹쳐도 일관된 메시지가 노출되며, 규칙 추가는 `MessageRule` 구현과 `priority` 지정만으로 확장 가능해졌다.
  시간 계산이 공통 기준으로 통합되어 테스트가 단순해졌고, 의료 지침 변경 시에도 기존 코드 영향 없이 안전하게 적용할 수 있게 되었다.

## 02 공용 데이터 계층 도입으로 앱과 위젯 상태 동기화

앱/위젯이 다른 저장소를 쓰는 구조를 하나로 단일화

- **문제**
  앱과 홈 화면 위젯이 각각 다른 SQLite 파일을 사용해 복용 기록을 관리하고 있었다. 사용자가 앱에서 복용 완료를 기록해도 위젯에는 이전 상태가 그대로 남아 있어, 서로 다른 안내 메시지가 동시에 노출되는 문제가 발생했다.
  Core Data 스키마가 변경될 때마다 앱과 위젯 저장소를 각각 마이그레이션해야 했고, 이 과정에서 데이터 이관 누락이나 기록 유실 위험도 존재했다. 사용자 입장에서는 어느 화면의 정보가 정확한지 혼란을 겪을 수밖에 없는 구조였다.

- **접근**
  앱과 위젯이 동일한 복용 상태를 사용하도록 공용 데이터 계층을 도입했다. App Group을 활용해 하나의 Core Data 저장소를 앱과 위젯이 함께 참조하도록 구성했다.
  스키마 변경에 대비해 자동 마이그레이션을 활성화해 데이터 이전 부담을 줄였다. 동시에 접근하는 상황을 고려해 최근 변경이 우선 반영되도록 충돌 처리 기준을 정리했다.
  데이터가 변경되면 공용 Repository에서 위젯을 갱신하며, 변경이 발생하면 홈 위젯과 앱 화면이 즉시 동기화되도록 했다.

- **결과**
  앱에서 복용 상태를 변경하면 위젯이 1초 이내에 동일한 상태로 업데이트되어, 두 화면 간 정보 불일치가 사라졌다.
  앱과 위젯이 동일한 SQLite 파일을 참조하게 되면서 데이터 동기화 문제를 구조적으로 차단할 수 있었다. Cascade 삭제 규칙과 자동 컨텍스트 병합 설정으로 데이터 정합성과 UI 최신 상태 유지가 함께 보장되었다.
  결과적으로 사용자에게는 일관된 복용 안내 경험이 제공되고, 개발 측면에서는 데이터 관리와 마이그레이션 부담이 크게 줄어들었다.

## 03 Diffable Data Source 기반 단일 셀 갱신 구조

캘린더 상태 변경 시 필요한 셀만 안정적으로 업데이트하는 UI 구조 개선

- **문제**
  캘린더 화면에서 특정 날짜의 복용 상태를 변경할 때마다 `reloadData()`가 호출되어 모든 셀이 다시 그려지고 있었다. 이로 인해 버튼을 누를 때마다 화면이 깜빡이거나 스크롤 위치가 초기화되는 문제가 발생했다.
  또한 IndexPath를 기준으로 셀을 직접 참조하는 구조였기 때문에, 데이터 변경 타이밍이 어긋나면 UI 업데이트 중 크래시가 발생할 위험도 있었다. 사용자 경험과 안정성 모두에서 개선이 필요한 상태였다.

- **접근**
  날짜 단위를 하나의 독립된 아이템으로 모델링해, 특정 날짜의 상태만 개별적으로 갱신할 수 있는 구조로 변경했다.
  컬렉션 뷰는 Diffable Data Source를 사용해 데이터 변경 사항을 안전하게 계산하도록 했고, 전체 화면을 다시 그리는 방식 대신 변경된 항목만 반영되도록 구성했다.
  상태 변경 시에는 해당 날짜 셀만 다시 설정되도록 처리해 불필요한 UI 갱신을 줄였다. 복용 상태 데이터는 ViewModel에서 단일 흐름으로 관리하고, UI는 이 변경 결과만 반영하도록 역할을 분리했다.
  이 구조를 통해 화면 깜빡임과 업데이트 충돌 가능성을 동시에 해소했다.

- **결과**
  복용 상태를 변경하면 해당 날짜 셀만 자연스럽게 갱신되고, 나머지 셀은 그대로 유지되어 화면 깜빡임이 사라졌다.
  Diffable Data Source가 항목의 식별자를 기준으로 변경 사항을 계산하므로, IndexPath 불일치로 인한 크래시 위험도 제거되었다.
  데이터 변경과 UI 갱신이 단방향 흐름으로 정리되어, 다른 화면이나 기능에서 상태를 변경해도 동일한 업데이트 경로를 재사용할 수 있게 되었다.
  결과적으로 캘린더 화면의 안정성과 사용자 체감 품질이 함께 개선되었다.

## 04 의료 규칙 기반 단위 테스트

복용 가이드의 안전성을 코드 수준에서 검증하는 테스트 체계 구축

- **문제**
  피임약 복용 로직은 시간 허용 범위, 하루 누락 시 대응, 연속 누락 시 주의 사항 등 의료 규칙을 정확히 반영해야 한다. 초기 구현에서는 서로 다른 규칙이 동시에 적용되는 상황에서 잘못된 메시지가 노출되는 버그가 발견되었다.
  특히 시간 경계값이나 "어제와 오늘 상태가 섞이는 경우"처럼 조건이 미묘한 시나리오는 재현 자체가 어려웠다. `Date()`를 직접 사용하는 구조로 인해 테스트 실행 시점에 따라 결과가 달라지는 문제도 있었다.

- **접근**
  시간에 의존하는 모든 로직을 `TimeProvider`로 분리해, 실제 시간 대신 고정된 시간을 주입할 수 있도록 구조를 변경했다. 이를 통해 복용 예정 시각 대비 정확히 몇 분, 몇 시간이 지났는지를 테스트 코드에서 명확히 설정할 수 있었다.
  복용 상태 생성, 메시지 계산, 상태 업데이트 등 핵심 UseCase 단위로 테스트를 나누어 의료 규칙을 직접 검증했다.
  또한 우선순위 기반 메시지 규칙이 충돌하지 않는지 확인하는 테스트를 추가해, 규칙 간 상호작용까지 함께 검증했다.

- **결과**
  시간 경계값과 연속 누락 계산 같은 민감한 로직을 실행 시각과 무관하게 안정적으로 검증할 수 있게 되었다.
  테스트 과정에서 우선순위 충돌과 연속 미복용 계산 오류를 발견해 로직을 사전에 수정할 수 있었다.
  새로운 의료 규칙이 추가될 경우에도 기존 테스트를 통해 회귀 여부를 즉시 확인할 수 있는 구조가 마련되었다.
  그 결과 복용 안내의 신뢰성이 높아졌고, 의료 규칙 변경에 대한 대응 속도와 안정성도 함께 개선되었다.

# Page 6 / 12 — 두섭이 (DoSurf) 핵심 구현 (Compact)

## 01 Watch-iPhone 양방향 동기화 충돌 해결
- 문제: Watch와 iPhone이 오프라인 상태에서 동일한 서핑 기록을 각각 수정한 뒤 재연결되면 데이터가 충돌해 일관성이 깨졌다. 나중에 수정한 데이터만 유지하면 먼저 수정한 변경이 손실되고, 양쪽 변경을 모두 보존하면 중복 기록이 생성되었다. 삭제한 기록이 다른 기기에서 수정될 때 삭제 정보가 전파되지 않아 다시 나타나는 문제도 있었다. WatchConnectivity의 비동기 특성상 동기화 시점을 예측하기 어려워, 충돌 해결 전략 없이는 데이터 무결성을 보장할 수 없었다.
- 접근: 수정 시각 기반 "최신 우선 병합 + 삭제 전파" 전략을 채택했다. 이 방식을 선택한 이유는 두 기기 모두 기록을 수정할 수 있어 단일 진실 소스를 고정할 수 없었고, 충돌 규칙이 명확해야 유지보수와 재현이 쉬웠기 때문이다. 각 기록에 lastModifiedAt과 deviceID를 추가해 수정 출처를 추적하고, 삭제는 isDeleted 플래그로 처리해 삭제 정보가 전파되도록 했다. 동일 시각 충돌은 deviceID 사전순으로 결정해 병합 결과가 항상 같도록 했다. WatchConnectivity로 양방향 통신을 유지하되, 변경된 필드만 보내는 증분 업데이트를 적용하고 배치 동기화와 자동 재시도 로직으로 전송 실패를 완화했다.
- 결과: 동시 수정 상황에서도 데이터 손실이나 중복 없이 일관된 기록이 유지되었고, 동기화 충돌로 인한 크래시가 0건으로 감소했다. 증분 업데이트로 메시지 크기가 평균 70% 줄어 배터리 소모가 감소했으며, 배치 동기화로 전송 횟수가 60% 줄었다. TestFlight 베타에서 양쪽 디바이스 기록이 항상 동일하다는 피드백을 확보했고, 데이터 불일치 문의가 사라졌다.

## 02 지역별 차트 조회 성능 개선
- 문제: 서퍼들이 당일 최적 스팟을 찾기 위해 3-5개 지역을 연속 조회하면서 매번 Firestore 요청이 발생했다. 각 요청이 평균 1.2초 걸려 5개 지역 비교 시 6초가 소요됐고, 이미 본 지역을 다시 선택해도 동일한 데이터를 재요청했다. 서핑 시즌 사용자 500명 기준 1인당 일평균 20회 조회면 월 30만 읽기가 발생해 무료 구간을 빠르게 초과할 위험이 있었다. 반복 대기 시간은 여러 지역을 빠르게 비교하는 흐름을 방해했다.
- 접근: 메모리 캐시와 prefetch를 결합했다. 이 방식을 선택한 이유는 응답 시간을 줄이면서도 서버 비용을 동시에 낮춰야 했기 때문이다. 캐시는 NSCache 기반 LRU로 구성해 최근 조회 데이터를 우선 보존하고, 메모리 부족 시 자동 정리되게 했다. 세션당 평균 7개 지역 조회 패턴을 고려해 최대 10개 항목을 캐싱하고, 차트당 50KB 수준으로 총 500KB를 넘지 않게 제한했다. Prefetch는 인접 지역과 과거 조회 이력을 활용해 다음에 볼 가능성이 높은 3개 지역을 백그라운드에서 미리 로드했다. 캐시 데이터는 즉시 표시하고, 백그라운드에서 최신 값을 가져와 변경이 있을 때만 UI를 갱신하는 stale-while-revalidate 방식을 적용했다.
- 결과: 캐시 히트율 70%를 달성해 불필요한 네트워크 요청이 50% 감소했고, Firebase 월 비용이 35% 절감되었다. 월 30만 읽기 중 15만 건이 캐시로 처리되어 과금 없이 운영 중이다. 캐시 히트 시 차트 표시 시간이 1.2초에서 0.3초로 75% 단축되었고, prefetch로 다음 지역 선택 시 즉시 표시 비율이 60%에 달했다. 여러 지역을 빠르게 비교하는 흐름이 개선되며 평균 세션 시간이 15% 증가했다.

## 03 Live Activities와 Dynamic Island 기반 실시간 세션 모니터링
- 문제: 서핑 세션 중 사용자는 iPhone을 방수 케이스에 넣어 해변에 두고 바다로 들어가므로, 상태를 확인하려면 젖은 손으로 기기를 꺼내 잠금 해제 후 앱을 열어야 했다. 앱을 열기까지의 마찰이 커서 "몇 분째 서핑 중인지", "몇 번의 파도를 탔는지" 같은 정보를 제때 확인하기 어려웠다. 서핑처럼 시간에 민감한 활동에서 이 마찰을 줄이는 것이 핵심 사용자 경험 과제였다.
- 접근: Live Activities와 Dynamic Island를 ActivityKit으로 구현해 잠금 화면과 노치 영역에서 실시간 세션 정보를 표시했다. 이 방식을 선택한 이유는 앱 실행 없이도 정보를 제공할 수 있고, 실시간 활동 추적에 맞는 시스템 UI를 활용할 수 있기 때문이다. ActivityAttributes로 고정 정보(시작 시간, 해변 이름)와 동적 정보(경과 시간, 라이딩 횟수, 평균 심박수)를 분리해 업데이트 효율을 높였다. 경과 시간은 1분 간격, 라이딩 횟수는 즉시, 심박수는 10초 간격으로 갱신해 정보 신선도와 배터리 효율을 균형화했다. 세션 진행에 따라 업데이트 빈도를 점진적으로 낮추고, Live Activity 탭 시 딥링크로 상세 화면으로 이동하도록 구성했다.
- 결과: 세션 상태 확인 빈도가 약 5배 증가했고, 앱을 열지 않고도 잠금 화면에서 즉시 확인 가능해 사용자 참여도가 높아졌다. iPhone을 꺼내는 빈도가 줄어 물 손상 위험이 낮아졌고, 라이딩 횟수의 실시간 확인으로 추가 활동 동기가 생겼다. 업데이트 빈도 조정으로 배터리 수명이 약 25% 연장되었으며, Dynamic Island 지원으로 최신 iOS 기능을 적극 활용하는 인상을 제공했다.

## 04 목업 데이터 기반 개발 전략
- 문제: 2025년 9월 26일 국가정보자원관리원 화재로 기상청 공공데이터포털 API가 약 2주간 중단되었다. DoSurf는 실시간 파도, 바람, 기상 데이터에 전적으로 의존하는 서비스로, API 중단 시 신규 기능 개발과 테스트가 불가능해졌다. 차트 렌더링, 날씨 분류 로직, 데이터 저장 등 핵심 기능 개발이 모두 멈춰 일정 지연이 불가피했다.
- 접근: API 중단 이전 수집한 실제 응답 구조를 분석해 Firestore에 목업 데이터 세트를 구축했다. 이 방식을 선택한 이유는 외부 API 의존성을 줄이면서 기존 비즈니스 로직을 변경하지 않아야 했기 때문이다. 프로토콜 기반 추상화로 데이터 출처를 분리해 ViewModel과 UseCase가 실제 API인지 목업인지 알 수 없게 했고, DTO는 기상청 API의 가변성을 반영해 Optional로 정의했다. 목업 데이터는 강릉, 포항, 제주, 부산 4개 지역 11개 해변의 3시간 간격 72시간 예보로 구성해 실제 쿼리 방식과 동일하게 동작하도록 했다.
- 결과: API 중단 기간에도 차트 렌더링, 날씨 분류, 서핑 기록 저장 등 핵심 기능 개발을 이어갔다. API 복구 후 데이터 수집 로직만 재개하면 되었고, 앱 코드는 수정 없이 실제 데이터로 전환됐다. 데이터 소스 격리 설계로 2주 이상의 일정 지연을 회피했고, 외부 API 장애 상황에서도 개발을 지속할 수 있는 대응 체계를 확보했다.

## 01 REST API 통신 계층과 토큰 인터셉터 기반 인증 자동화
- 문제: Spring + AWS 기반 REST API 20개 엔드포인트의 응답 형식이 제각각이라 디코딩과 에러 처리가 화면마다 달랐다. 동일한 401도 만료와 권한 부족을 구분해야 했고, Firebase 로그인 뒤 백엔드 JWT를 교환해 Access/Refresh 토큰을 요청마다 맞게 첨부해야 했다. 초기 구현은 Codable 정의와 분기 처리로 API 1개당 평균 2시간이 소요되었고, 20개로 확장 시 일정 리스크가 컸다.
- 접근: 백엔드와 협의해 응답을 ApiResponse<T>로 통일하고 NetworkService에서 공통 디코딩을 수행했다. 성공은 data를 반환하고 실패는 HTTP 상태 코드와 error.code를 함께 매핑해 NetworkError로 변환했다. 이 방식을 선택한 이유는 ViewModel에서 처리해야 할 분기와 중복을 줄여야 했고, API 수가 많아질수록 표준화의 효율이 커졌기 때문이다. 인증은 RequestInterceptor 패턴의 adapt 단계에서 자동으로 헤더를 추가하도록 구성했다. requiresAuth/usesRefreshToken 플래그로 Access 또는 Refresh 토큰을 구분해 실수 가능성을 낮췄고, TokenManager가 Keychain에서 최신 값을 읽도록 했다.
- 결과: 디코딩 실패율은 15%에서 0.5% 미만으로 감소했고, 에러 원인 파악 시간은 평균 30분에서 5분으로 단축되었다. API 1개당 개발 시간이 2시간에서 20분 수준으로 줄어 20개 엔드포인트를 1주일 내 완성했다. 모든 화면이 동일한 에러 처리 로직을 공유해 유지보수가 쉬워졌고, 토큰 타입 실수와 인증 관련 버그가 줄었다.

## 02 Keychain 기반 토큰 보안 저장
- 문제: 초기에는 Access Token과 Refresh Token을 UserDefaults에 저장했다. 자동 로그인 기능을 테스트하는 동안에는 문제가 없어 보였고, 앱을 종료하고 다시 열어도 토큰이 유지되어 사용자가 로그인 화면을 거치지 않고 메인 화면으로 진입했다. 문제는 보안 검토 과정에서 드러났다. UserDefaults는 평문으로 저장되어 탈옥된 기기나 백업 파일에서 데이터를 읽을 수 있었고, Access Token이 노출되면 해당 사용자로 위장한 API 호출이, Refresh Token까지 노출되면 무한정 토큰 갱신이 가능했다. KIDK는 아동의 용돈 데이터를 다루므로 토큰 탈취는 개인정보 유출로 직결되었다.
- 접근: 시스템 레벨 암호화 저장소인 Keychain을 도입하여 토큰을 보관했다. 보안 API를 래핑한 클래스를 만들고 Access Token과 Refresh Token을 구분하여 저장했으며, 저장 시도 시 이미 존재하는 항목은 자동으로 업데이트하도록 했다. 저장소 인터페이스를 분리하여 테스트 환경에서는 실제 보안 저장소 대신 임시 메모리를 사용하도록 했다. 로그아웃 기능은 두 토큰을 모두 삭제하는 단일 메서드로 구현했으며, 서버 요청 실패 여부와 관계없이 로컬 데이터는 항상 정리되도록 보장했다.
- 결과: Keychain 도입으로 토큰 탈취 위험이 제거되었다. UserDefaults 사용 시 백업 파일에서 평문 토큰을 추출할 수 있었으나, Keychain 적용 후 암호화된 저장소로 보호되어 동일한 공격 방법이 차단되었다. 탈옥 기기에서도 추가 공격 없이는 토큰에 접근할 수 없게 되었고, 아동 용돈 데이터를 다루는 앱의 보안 요구사항을 충족했다. 저장소 추상화를 통해 다른 민감 데이터도 동일한 보안 수준으로 보호할 수 있는 기반이 마련되었다.

## 03 Firebase-백엔드 이중 인증 흐름 통합
- 문제: Firebase Authentication과 백엔드 JWT를 함께 쓰는 구조라 사용자는 Firebase로 로그인하지만, 실제 API 호출에는 백엔드가 발급한 Access/Refresh 토큰이 필요했다. Firebase 로그인만으로는 API를 호출할 수 없고, 백엔드 로그인만 구현하면 Firebase 보안 이점을 잃는다. ID Token과 UID를 받은 뒤 백엔드에서 JWT를 교환해 저장하는 순차 흐름이 필요했으며, 단계별 실패 원인을 구분해 안내해야 했다.
- 접근: Firebase 비동기 처리를 RxSwift 스트림으로 변환해 로그인 성공 시 백엔드 로그인으로 이어지는 2단계 체인을 구성했다. 이 방식을 선택한 이유는 중첩 콜백을 줄이고, 실패 지점을 명확히 구분해 사용자 메시지를 일관되게 처리하기 위해서다. 성공 시 사용자 정보와 토큰을 저장하고, 실패는 동일한 에러 경로로 전파해 화면에서 분기 처리를 최소화했다. 자동 로그인은 저장된 설정을 불러오고, 로그인 성공 시 이메일을 저장해 다음 실행 시 자동 채움이 되도록 했다.
- 결과: Firebase 로그인 후 백엔드 로그인을 순차적으로 실행하는 흐름이 명확해졌고, 실패 지점을 구분해 안내할 수 있었다. 로그인 UI는 단일 경로로 정리되어 유지보수가 쉬워졌으며, 이메일 자동 채움으로 사용자가 비밀번호만 입력하면 되는 경험을 제공했다. 두 인증 시스템이 한 절차로 연결되어 사용자는 별도의 추가 인증을 인지하지 않게 되었다.

## 04 Vision 프레임워크 기반 영수증 OCR 자동 파싱

- 접근: Vision 텍스트 인식을 accurate 모드로 설정하고 Document Camera로 영수증 경계를 자동 보정했다. 처리 시간을 조금 늘리더라도 금액 인식의 정확도가 중요하다고 판단했기 때문이다. 결제 금액은 "합계/총액/결제금액/total" 키워드 주변의 숫자를 우선 추출하고, 키워드가 없으면 가장 큰 숫자를 선택했다. 상호명은 첫 5줄에서 유효 길이의 가장 긴 줄을 선택해 전화번호나 주소 오인식을 줄였다. 결과는 입력 필드에 자동 채우되 사용자가 수정할 수 있도록 하고, 모든 필드가 채워져야 저장이 가능하도록 검증했다.

## 01 Combine 기반 MVI 단방향 아키텍처 설계
- 문제: 기존 프로젝트들은 모두 MVVM + RxSwift 조합을 사용해 양방향 바인딩으로 인한 상태 추적 어려움과 복잡한 데이터 흐름이 발생했다. 화면이 복잡해질수록 어떤 이벤트가 어떤 상태 변경을 일으키는지 파악하기 어려웠고, 디버깅 시 상태 변화를 역추적하는 데 시간이 많이 소요되었다.
- 접근: Intent → Model → View의 단방향 흐름을 강제하는 MVI 패턴을 Combine으로 구현했다. 사용자 액션은 Intent enum으로 정의하고, Model이 Intent를 받아 새로운 State를 생성하며, View는 State를 구독해 UI를 갱신한다. 상태 변경은 반드시 Intent를 통해서만 발생하도록 제한해 예측 가능한 흐름을 확보했다. CurrentValueSubject로 현재 상태를 유지하고, PassthroughSubject로 Intent를 전달해 Combine의 Publisher/Subscriber 패턴을 직접 활용했다.
- 결과: 모든 상태 변경이 Intent로 시작되어 디버깅 시 흐름 추적이 명확해졌다. RxSwift 없이 Combine만으로 반응형 프로그래밍을 구현해 외부 의존성이 제거되었고, SwiftUI의 선언적 UI와 MVI의 단방향 흐름이 자연스럽게 결합되어 코드 가독성이 향상되었다.

## 02 지도 클러스터링과 동적 매물 로딩
- 문제: 수천 개의 매물 마커를 지도에 한꺼번에 표시하면 렌더링 성능이 급격히 저하되고, 마커가 겹쳐 개별 매물을 식별하기 어려웠다. 지도를 이동할 때마다 전체 매물을 다시 요청하면 네트워크 비용과 응답 시간이 증가했다.
- 접근: MapKit의 MKClusterAnnotation을 활용해 줌 레벨에 따라 인접 마커를 자동으로 그룹화했다. 클러스터를 탭하면 해당 영역으로 줌인되고, 개별 마커가 드러나면 상세 정보를 표시한다. 지도 영역 변경 시 Combine의 debounce로 연속 이동을 묶어 API 호출 횟수를 줄이고, 현재 보이는 영역의 매물만 요청하는 뷰포트 기반 로딩을 적용했다.
- 결과: 1,000개 이상의 매물도 60fps를 유지하며 부드럽게 렌더링되고, 클러스터링으로 밀집 지역의 매물 밀도를 직관적으로 파악할 수 있다. debounce와 뷰포트 로딩으로 불필요한 API 호출이 80% 감소해 응답 속도와 배터리 효율이 개선되었다.

## 03 SwiftUI + Combine을 활용한 실시간 필터링
- 문제: 사용자가 가격, 면적, 카테고리 등 여러 필터를 조합해 매물을 검색할 때, 각 필터 변경마다 별도 API를 호출하면 응답 지연과 UI 깜빡임이 발생했다. 필터 상태 관리가 분산되어 현재 적용된 조건을 파악하기 어려웠다.
- 접근: 모든 필터 조건을 단일 FilterState 구조체로 통합하고, @Published 프로퍼티로 변경을 감지한다. Combine의 combineLatest로 여러 필터 변경을 하나의 스트림으로 병합하고, debounce로 연속 입력을 묶어 최종 값만 API에 전달한다. 결과는 즉시 UI에 반영하고, 네트워크 응답이 오면 갱신하는 optimistic update를 적용해 체감 속도를 높였다.
- 결과: 필터 변경 시 0.3초 이내에 결과가 반영되어 실시간 검색 느낌을 제공한다. 단일 FilterState로 현재 조건을 한눈에 파악할 수 있고, 필터 초기화도 단일 메서드로 처리된다. debounce로 API 호출이 70% 감소해 서버 부하와 사용자 대기 시간이 줄었다.

## 04 Repository 패턴 기반 데이터 소스 추상화
- 문제: 서버가 종료되거나 API가 변경되면 앱 전체가 동작하지 않는 구조는 포트폴리오 시연에 치명적이다. ViewModel이 네트워크 레이어를 직접 호출하면 서버 의존성이 코드 전반에 퍼져, 목업 전환 시 수십 개 파일을 수정해야 했다. 테스트 환경에서도 실제 서버를 호출해야 해 CI/CD 파이프라인이 불안정했다.
- 접근: PropertyRepository 프로토콜로 데이터 접근 인터페이스를 정의하고, RemoteRepository와 MockRepository를 각각 구현했다. ViewModel은 프로토콜 타입만 의존하고, 실제 구현체는 앱 시작 시점에 환경변수로 결정해 주입한다. Mock 데이터는 실제 API 응답 구조를 그대로 반영한 JSON 파일로 구성해, 서버가 없어도 모든 화면과 흐름을 완전히 시연할 수 있다. 북마크와 최근 검색은 Realm으로 로컬 저장하고, @ObservedResults로 SwiftUI와 반응형으로 연동했다.
- 결과: 빌드 설정 하나로 서버/목업 전환이 가능해 서버 종료 후에도 앱이 완전히 동작한다. ViewModel 코드 수정 없이 데이터 소스를 교체할 수 있어 유지보수가 용이하고, Mock 환경에서 단위 테스트를 안정적으로 수행할 수 있다. 프로토콜 추상화를 통해 향후 다른 API나 로컬 DB로 전환해도 영향 범위가 Repository 구현체로 한정된다.
