## 핵심 구현


## 01 Watch-iPhone 양방향 동기화 충돌 해결
타임스탬프 기반 병합 전략으로 데이터 손실 없는 양방향 동기화 구현

**문제**
Watch와 iPhone이 `오프라인` 상태에서 각각 동일한 서핑 기록을 수정한 뒤 `재연결` 시 수정본이 엇갈리며 기록이 `중복`되거나 `유실`되었다. 단순 병합을 시도하면 동일 레코드가 두 건으로 분기됐다. 특히 한쪽에서 기록을 `삭제`하고 다른 쪽에서 `수정`한 경우, 삭제 정보가 동기화되지 않아 이미 삭제된 기록이 다시 나타나는 현상도 발생했다. `WatchConnectivity`의 비동기 특성상 두 디바이스가 `동기화 시점을 예측하기 어려워`, 충돌 해결 전략 없이는 `데이터 무결성을 보장할 수 없었다`.

**접근**
타임스탬프를 기준으로 `최신 우선 병합`과 `삭제 전파` 전략을 채택했다. 각 기록에 `lastModifiedAt`과 `deviceID`를 추가해 `수정 출처`를 추적하고, 삭제는 `isDeleted` 플래그로 처리해 삭제 정보가 동기화되도록 했다. 이 방식을 선택한 이유는 두 기기 모두 기록을 수정할 수 있어 단일 진실 소스를 고정할 수 없었고, 충돌 규칙이 명확해야 유지보수와 재현이 쉬웠기 때문이다.
전체 데이터가 아닌 변경된 필드만 전송하는 `증분 업데이트`를 적용했다. 충돌 해결 로직은 `삭제 우선`, 다음으로 `최신 수정 시각 우선`, 그다음 `디바이스 식별자 사전순 선택` 규칙을 적용했다. 여러 기록은 `배치 전송`했고, 실패 시 `재시도` 로직을 추가했다.

**결과**
Watch와 iPhone에서 동시 수정이 발생해도 `데이터 손실/중복` 없이 일관된 기록이 유지되었고, 동기화 충돌로 인한 크래시가 `0건`으로 감소했다. `증분 업데이트`로 메시지 크기가 평균 `70%` 감소해 배터리 소모가 줄었고, 배치 동기화는 메시지 전송 횟수를 `60%` 감소시켜 블루투스 부하를 낮췄다.

## 02 지역별 차트 조회 성능 개선

LRU 메모리 캐시와 예측 prefetch로 차트 로딩 지연을 줄이고 Firestore 읽기 비용을 절감

**문제**
서퍼가 당일 최적의 스팟을 찾기 위해 여러 지역을 연속으로 조회할 때, 지역을 바꿀 때마다 `Firestore`에서 데이터를 다시 받아와 대기 시간이 계속 누적되었다. `5개 지역`을 비교하면 총 대기 시간이 `약 6초`까지 늘어나 화면 전환 흐름이 끊겼다. 이미 조회한 지역을 다시 선택해도 같은 데이터를 `재요청`하는 구조라서, 사용자가 왕복 탐색을 할수록 체감 속도가 더 나빠졌다. 시즌처럼 조회가 몰리는 기간에는 `읽기 요청`이 급증해 운영 비용이 커질 위험도 있었다. 결과적으로 속도와 비용을 동시에 개선할 필요가 있었다.

**접근**
최근에 본 지역 차트 데이터는 다시 내려받지 않도록, iOS의 `NSCache`를 사용해 `LRU 캐시`를 구성했다. 사용자가 다음에 누를 가능성이 높은 인접 지역은 미리 받아두는 `prefetch`를 적용해 화면 전환 전에 데이터를 준비하도록 했다. 화면에는 캐시 데이터를 먼저 즉시 보여주고, 동시에 백그라운드에서 최신 데이터를 다시 받아 갱신하는 `stale-while-revalidate` 패턴을 적용해 체감 속도와 최신성을 함께 챙겼다. 캐시와 프리패치 로직은 `ChartCacheManager`로 분리해 화면 코드는 “가져오기 요청”만 하도록 단순화했다. 메모리 사용이 무제한으로 늘지 않도록 `캐시 상한`을 두고, 세션 패턴에 맞춰 적절한 범위만 유지하도록 조정했다.

**결과**
`캐시 히트율 70%`를 달성해 `Firestore 읽기 요청`이 `50%` 감소했다. 차트가 화면에 보이기까지 걸리는 시간은 `1.2초`에서 `0.3초`로 단축되어, 지역을 바꿔도 끊김이 크게 줄었다. `prefetch` 적용 이후에는 다음 지역을 눌렀을 때 즉시 표시되는 비율이 `60%`까지 올라가 연속 탐색 경험이 매끄러워졌다. 불필요한 읽기 요청이 줄면서 월 운영 비용도 `35%` 절감되었다. 속도 개선과 비용 절감이 동시에 발생해, 성수기 트래픽에서도 더 안정적으로 운영할 수 있는 기반이 만들어졌다.



## 03 Live Activities와 Dynamic Island 기반 실시간 세션 모니터링

잠금 화면 통합으로 앱 실행 없는 세션 상태 확인 구현

**문제**
서핑 세션 진행 중 사용자는 iPhone을 방수 케이스에 넣어 해변에 두고 바다로 들어가므로, 세션 진행 상황을 확인하려면 젖은 손으로 iPhone을 꺼내 잠금 해제 후 앱을 열어야 했다. 전통적으로 앱은 사용자가 명시적으로 열어야만 정보를 볼 수 있어, 실시간으로 진행되는 활동을 추적하는 앱에게는 치명적인 제약이었다. 사용자는 "지금 몇 분째 서핑 중인지", "몇 번의 파도를 탔는지" 같은 정보를 빠르게 확인하고 싶어 했지만, 앱을 열기까지의 마찰이 너무 컸고, 서핑처럼 시간에 민감한 활동에서는 지속적인 상태 확인을 위해 이 마찰을 줄이는 것이 핵심 사용자 경험 문제였다.

**접근**
`iOS 16`의 `Live Activities`와 `Dynamic Island`를 `ActivityKit`으로 구현해 잠금 화면과 노치 영역에서 실시간 세션 정보를 표시했다. `ActivityAttributes`로 고정 정보(시작 시간, 해변 이름)와 동적 정보(경과 시간, 라이딩 횟수, 평균 심박수)를 분리해 업데이트 효율성을 높였고, 경과 시간은 `1분 간격`, 라이딩 횟수는 `즉시`, 심박수는 `10초 간격`으로 업데이트해 정보 신선도와 배터리 효율의 균형을 맞췄다. `Widget Extension`에서 `SwiftUI`로 Dynamic Island의 축소/확장/최소 상태별 레이아웃을 구성하고, 라이딩 횟수 증가 시 페이드 애니메이션과 심박수 임계값 초과 시 펄스 애니메이션을 적용해 변화를 즉시 인지하게 했다. 배터리 최적화를 위해 업데이트 빈도를 `동적 조정`했고, Live Activity 탭 시 `딥링크`로 세션 상세 화면 이동, 길게 누르면 `조기 종료` 옵션을 제공했다.

**결과**
사용자가 세션 상태를 확인하는 빈도가 `약 5배` 증가했고, 앱을 열지 않고도 `잠금 화면`에서 즉시 확인 가능해져 사용자 참여도가 높아졌다. iPhone을 방수 케이스에서 꺼내는 빈도가 감소해 물 손상 위험이 낮아졌고, 라이딩 횟수 실시간 확인으로 "한 번 더 타자"는 동기 부여 효과가 발생했다. 업데이트 빈도 `동적 조정`으로 배터리 수명이 `약 25%` 연장되었으며, `Dynamic Island` 지원으로 앱이 최신 iOS 기능을 적극 활용한다는 긍정적 이미지를 형성했다. 사용자는 앱을 열지 않고도 필요한 정보를 즉시 확인할 수 있게 되어, 기술이 흐름을 방해하지 않고 자연스럽게 통합되었다.

**문제**

**결과**

## 01 의료 안전 기준을 반영한 메시지 우선순위 엔진

복용 상태에 따라 필요한 안내를 정확한 규칙으로 제공하는 구조

**문제**
복용을 `하루 누락`했을 때와 `연속 누락`했을 때 안내가 다르지만, 하나의 `긴 조건문`에 섞여 있어 어떤 상황이 더 위험한지 `우선순위`가 드러나지 않았다. `이틀 연속 누락`과 `2시간 지연`이 동시에 발생하면 어떤 메시지를 우선할지 명시되지 않아 잘못된 안내 위험이 있었다.

**접근**
의료 가이드라인의 `위험도가 높은 상황을 먼저 안내` 원칙을 코드에 반영했다. 각 메시지 조건을 `MessageRule` 프로토콜을 따르는 `독립 객체`로 분리하고, `priority`(규칙 평가 순서를 정하는 정수로 낮은 값일수록 우선 평가)를 부여했다. `MessageRuleEngine`은 규칙을 `우선순위 정렬`로 `순차 평가`하고 `첫 매칭` 메시지만 반환하도록 했으며, 예정 시각 대비 `시간 차이 단계화`로 모든 규칙이 동일한 기준으로 시간을 계산하게 했다.

**결과**
위험도가 높은 상황이 항상 먼저 안내되어 누락·지연이 겹쳐도 `일관된 메시지`가 노출되며, 규칙 추가는 `MessageRule` 구현과 `priority` 지정만으로 `확장` 가능해졌다. 시간 계산이 `공통 기준`으로 통합되어 테스트가 단순해졌고, 의료 지침 변경 시에도 기존 코드 영향 없이 안전하게 적용할 수 있게 되었다.

## 02 공용 데이터 계층 도입으로 앱과 위젯 상태 동기화

앱/위젯이 다른 저장소를 쓰는 구조를 하나로 단일화

**문제**
앱과 홈 화면 위젯이 각각 다른 `SQLite` 파일을 사용해 복용 기록을 관리하고 있었다. 사용자가 앱에서 복용 완료를 기록해도 위젯에는 이전 상태가 그대로 남아 있어, `정보 불일치`로 서로 다른 안내 메시지가 동시에 노출되는 문제가 발생했다. `Core Data` 스키마가 변경될 때마다 앱과 위젯 저장소를 각각 `마이그레이션`해야 했고, 이 과정에서 데이터 이관 누락이나 기록 `유실` 위험도 존재했다. 사용자 입장에서는 어느 화면의 정보가 정확한지 혼란을 겪을 수밖에 없는 구조였다.

**접근**
앱과 위젯이 동일한 복용 상태를 사용하도록 `공용 데이터 계층`을 도입했다. `App Group`을 활용해 하나의 `Core Data 저장소`를 앱과 위젯이 함께 참조하도록 구성했다. 스키마 변경에 대비해 `자동 마이그레이션`을 활성화해 데이터 이전 부담을 줄였다. 동시에 접근하는 상황을 고려해 최근 변경이 우선 반영되도록 `충돌 처리 기준`을 정리했다. 데이터가 변경되면 `공용 Repository`에서 위젯을 갱신하며, 변경이 발생하면 홈 위젯과 앱 화면이 즉시 `동기화`되도록 했다.

**결과**
앱에서 복용 상태를 변경하면 위젯이 `1초 이내`에 동일한 상태로 업데이트되어, 두 화면 간 정보 불일치가 사라졌다. 앱과 위젯이 동일한 `SQLite` 파일을 참조하게 되면서 데이터 동기화 문제를 구조적으로 차단할 수 있었다. `Cascade 삭제` 규칙과 `자동 컨텍스트 병합` 설정으로 데이터 `정합성`과 UI 최신 상태 유지가 함께 보장되었다. 결과적으로 사용자에게는 일관된 복용 안내 경험이 제공되고, 개발 측면에서는 데이터 관리와 마이그레이션 부담이 크게 줄어들었다.

## 03 Diffable Data Source 기반 단일 셀 갱신 구조

캘린더 상태 변경 시 필요한 셀만 안정적으로 업데이트하는 UI 구조 개선

**문제**
캘린더 화면에서 특정 날짜의 복용 상태를 변경할 때마다 `reloadData()`가 호출되어 `모든 셀`이 다시 그려지고 있었다. 이로 인해 버튼을 누를 때마다 화면이 `깜빡이거나` 스크롤 위치가 `초기화`되는 문제가 발생했다. 또한 `IndexPath`를 기준으로 셀을 직접 참조하는 구조였기 때문에, 데이터 변경 타이밍이 어긋나면 UI 업데이트 중 `크래시`가 발생할 위험도 있었다. 사용자 경험과 안정성 모두에서 개선이 필요한 상태였다.

**접근**
날짜 단위를 하나의 `독립 아이템`으로 모델링해, 특정 날짜의 상태만 `개별 갱신`할 수 있는 구조로 변경했다. 컬렉션 뷰는 `Diffable Data Source`를 사용해 데이터 변경 사항을 안전하게 계산하도록 했고, 전체 화면을 다시 그리는 방식 대신 `변경된 항목만 반영`되도록 구성했다. 상태 변경 시에는 해당 날짜 셀만 다시 설정되도록 처리해 불필요한 UI 갱신을 줄였다. 복용 상태 데이터는 `ViewModel`에서 `단일 흐름`으로 관리하고, UI는 이 변경 결과만 반영하도록 역할을 분리했다. 이 구조를 통해 화면 깜빡임과 업데이트 충돌 가능성을 동시에 해소했다.

**결과**
복용 상태를 변경하면 해당 날짜 셀만 `자연스럽게 갱신`되고, 나머지 셀은 그대로 유지되어 화면 깜빡임이 사라졌다. `Diffable Data Source`가 항목의 `식별자`를 기준으로 변경 사항을 계산하므로, `IndexPath 불일치`로 인한 크래시 위험도 제거되었다. 데이터 변경과 UI 갱신이 `단방향 흐름`으로 정리되어, 다른 화면이나 기능에서 상태를 변경해도 동일한 업데이트 경로를 재사용할 수 있게 되었다. 결과적으로 캘린더 화면의 안정성과 사용자 체감 품질이 함께 개선되었다.

## 04 의료 규칙 기반 단위 테스트

복용 가이드의 안전성을 코드 수준에서 검증하는 테스트 체계 구축

**문제**
피임약 복용 로직은 시간 허용 범위, 하루 누락 시 대응, 연속 누락 시 주의 사항 등 `의료 규칙`을 정확히 반영해야 한다. 초기 구현에서는 서로 다른 규칙이 동시에 적용되는 상황에서 잘못된 메시지가 노출되는 버그가 발견되었다. 특히 `시간 경계값`이나 “어제와 오늘 상태가 섞이는 경우”처럼 조건이 미묘한 시나리오는 재현 자체가 어려웠다. `Date()`를 직접 사용하는 구조로 인해 테스트 실행 시점에 따라 결과가 달라지는 문제도 있었다.

**접근**
시간에 의존하는 모든 로직을 `TimeProvider`로 분리해, 실제 시간 대신 `고정된 시간 주입`이 가능하도록 구조를 변경했다. 이를 통해 복용 예정 시각 대비 정확히 몇 분, 몇 시간이 지났는지를 테스트 코드에서 명확히 설정할 수 있었다. 복용 상태 생성, 메시지 계산, 상태 업데이트 등 핵심 `UseCase 단위`로 테스트를 나누어 의료 규칙을 직접 검증했다. 또한 `우선순위 기반 메시지 규칙`이 충돌하지 않는지 확인하는 테스트를 추가해, 규칙 간 `상호작용`까지 함께 검증했다.

**결과**
시간 경계값과 연속 누락 계산 같은 민감한 로직을 실행 시각과 무관하게 안정적으로 검증할 수 있게 되었다. 테스트 과정에서 `우선순위 충돌`과 `연속 미복용 계산 오류`를 발견해 로직을 사전에 수정할 수 있었다. 새로운 의료 규칙이 추가될 경우에도 기존 테스트를 통해 `회귀` 여부를 즉시 확인할 수 있는 구조가 마련되었다. 그 결과 복용 안내의 신뢰성이 높아졌고, 의료 규칙 변경에 대한 대응 속도와 안정성도 함께 개선되었다.

## 01 자동 배경 제거와 고해상도 이미지 저장

사진 편집 품질과 사용 경험을 동시에 개선한 이미지 처리 구조

**문제**
사진에서 인물만 분리해 사용하는 기능은 사용자 만족도에 직접적인 영향을 준다. 기존 방식은 배경 제거 정확도가 낮아 머리카락이나 윤곽 부분을 사용자가 직접 수정해야 하는 경우가 많았다. 또한 편집 중 실수했을 때 되돌릴 수 있는 기능이 없어 작업 부담이 컸다. 최종 저장되는 이미지 해상도도 기기 화면 기준에 묶여 있어 인쇄나 재사용에 한계가 있었다.

**접근**
사진에서 사람을 자동으로 인식하기 위해 Apple의 `Vision` 프레임워크를 사용해 `전경 마스크`를 생성했다. 이 과정에서 사람이 있는 영역만 추출하고 배경은 투명하게 처리하여 기본 품질을 높였다. 편집 과정 전체는 하나의 `ViewModel`에서 관리해, 배경 제거 상태와 수동 보정 내용, 되돌리기 기록을 한 흐름으로 연결했다. 편집 중에는 가벼운 저해상도 이미지를 사용해 반응 속도를 유지하고, 저장 시에는 `ImageRenderer`의 `scale` 값을 높여 고해상도 이미지를 다시 생성하도록 분리했다. 브러시와 지우개는 `Canvas`의 `blendMode`를 활용해 하나의 화면에서 자연스럽게 전환되도록 구성했다.

**결과**
`자동 배경 제거 정확도`가 개선되어 대부분의 사진은 추가 보정 없이 바로 사용할 수 있었다. `되돌리기/다시하기`를 지원해 편집 실수에 대한 부담을 줄였고, `최종 저장 이미지 고해상도 출력`으로 해상도 한계를 해소했다. 또한 `편집 흐름 단순화`로 사진 선택부터 저장까지 작업이 끊기지 않았다. 다만 편집 기록을 이미지로 보관하는 구조라 장시간 편집 시 `메모리 사용량 증가` 한계가 있었다.

## 02 앨범 썸네일 프리패치와 다운샘플링

많은 사진을 빠르고 안정적으로 보여주기 위한 앨범 로딩 방식

**문제**
스마트폰 앨범의 사진은 원본 크기가 매우 커서 그대로 불러오면 메모리를 많이 사용한다. 3열 앨범 화면에서는 한 번에 15장 이상이 동시에 표시되는데, 이때 원본 이미지를 사용하면 스크롤이 끊기거나 앱이 종료될 수 있었다. 특히 빠르게 스크롤할 경우 같은 이미지를 반복해서 다시 불러오는 일이 많아 성능 저하가 더 심해졌다. 이로 인해 앨범을 탐색하는 기본 동작 자체가 불안정해지는 문제가 있었다.

**접근**
앨범 접근은 iOS의 `Photos` 프레임워크를 사용하되, `PHCachingImageManager`를 통해 이미지를 관리하도록 구조를 정리했다. 처음 앨범에 들어올 때는 전체 사진을 한 번에 불러오지 않고, 최근 `60장`만 먼저 가져오는 방식으로 로딩 범위를 제한했다. 사용자가 스크롤을 내려 화면 하단에 가까워지면 다음 `60장`을 추가로 불러오는 `페이지네이션`을 적용했다. 썸네일 이미지는 실제 화면에 보이는 크기에 맞춰 요청하도록 하고, 원본 크기는 선택이 필요한 순간에만 사용했다. 앱에 저장된 이미지의 경우에는 `Core Graphics`의 `CGImageSource`를 이용해, 필요한 크기만 메모리에 펼치는 `다운샘플링` 방식을 적용했다. 또한 이미 한 번 불러온 이미지는 `캐시`에 저장해, 다시 스크롤로 등장할 때 즉시 사용할 수 있도록 했다.

**결과**
앨범 진입 시 로딩 대상이 제한되면서 초기 화면이 빠르게 표시되었다. 썸네일이 화면 크기에 맞춰 로드되면서 메모리 사용량이 크게 줄어들었고, 여러 장이 동시에 보여져도 앱이 안정적으로 동작했다. 빠른 스크롤 후 다시 위로 이동해도 이미지가 즉시 나타나 사용자 체감 성능이 개선되었다. 실제 테스트에서도 메모리 사용량이 크게 감소했고, 화면 전환과 스크롤이 부드럽게 유지되었다. 다만 현재 구조는 스크롤 방향을 미리 예측해 이미지를 준비하지는 않기 때문에, 향후 `PHCachingImageManager`의 프리패치 기능을 적극 활용하면 추가 개선 여지가 있다.

## 03 번역 관리 프로세스 정리
비개발자도 시트에서 수정하고 Xcode에는 자동 반영되게 구성

**문제**
새로운 기능이 추가될 때마다 개발자가 화면 문구를 만들고 번역 키를 직접 정의한 뒤, 각 언어의 `Localizable.stringsdict`에 수동으로 입력해야 했다. 문구는 디자이너와 PM 검수 과정에서 자주 바뀌었고, 변경될 때마다 개발자가 다시 파일을 수정하는 작업이 반복되었다. 언어별 파일이 분리되어 있어 특정 언어의 키 추가나 수정이 누락된 채로 배포되는 일이 있었고, 업데이트 이후에야 문제를 발견하는 경우가 잦았다. 번역 담당자는 `Xcode`나 `Git`을 사용할 수 없어 직접 `stringsdict`를 수정하지 못했고, 작은 수정도 개발자가 대신 처리해야 해서 병목이 생겼다. 결과적으로 누락 번역이나 오역이 배포 이후에 발견되어 긴급 수정이 필요한 문제가 있었다.

**접근**
번역 텍스트의 작업 공간을 `Xcode` 밖으로 분리해, 비개발자 팀원들이 `구글 시트`에서 문구를 직접 수정할 수 있도록 했다. 시트에는 키와 문구, 검수 상태를 함께 두고, 팀원이 `변경 완료`로 상태를 바꾸면 자동으로 반영 파이프라인이 동작하도록 연결했다. 자동 반영 단계에서는 구글 시트의 값을 `Localizable.stringsdict` 형식으로 변환해 iOS 프로젝트의 로컬라이제이션 리소스에 적용되도록 구성했다. 이 과정이 끝나면 어떤 앱 버전에 반영되었는지 기록이 남도록, `빌드 버전` 정보와 함께 반영 로그를 자동으로 저장했다. 동시에 로컬라이제이션 변경이 실제로 언제 코드베이스에 들어갔는지를 추적할 수 있도록, 반영 시점의 `커밋` 정보도 자동으로 기록되게 했다. 결과적으로 번역 변경은 `시트에서 확정`과 `Xcode 반영`이 분리되지 않고 한 흐름으로 이어지며, 문구 변경의 책임 소재와 추적 가능성이 확보되었다.

**결과**
번역 문구 수정은 `구글 시트`에서 `변경 완료`로 표시하는 것만으로 반영 흐름이 시작되어, 개발자가 매번 로컬라이제이션 파일을 열고 복사해 붙여넣는 반복 작업이 크게 줄었다. 문구 변경이 확정되기 전까지는 앱 코드 수정이 발생하지 않아, 디자이너와 PM 검수 과정에서 생기던 잦은 재반영 요청도 부담이 감소했다. 반영 시점에 어떤 앱 버전에 포함되었는지와 해당 로컬라이제이션이 언제 `커밋`되었는지가 자동으로 기록되어, “언제 바뀌었는지 알기 어렵다”는 문제가 해소되었다. 그 결과 배포 이후에 번역 누락이나 오역을 뒤늦게 발견해 긴급 수정으로 대응하는 상황이 줄었고, 문제가 발생하더라도 변경 이력을 근거로 원인을 빠르게 추적할 수 있게 되었다. 비개발자 팀원들이 개발 도구 없이도 번역 작업을 완료할 수 있어 협업 속도가 빨라졌고, 개발자는 기능 개발 흐름을 방해받지 않고 일정에 집중할 수 있었다.

## 01 REST API 통신 계층과 토큰 인터셉터 기반 인증 자동화

공통 응답 래퍼와 요청 인터셉터로 `20개 엔드포인트`의 디코딩과 인증 처리를 한 흐름으로 통일했다.

**문제**
Spring과 AWS 환경의 백엔드와 연결된 `REST API 20개`를 iOS에서 구현해야 했지만, 엔드포인트마다 응답 형태가 달라 매번 처리 방식이 달라졌다. 어떤 API는 배열을 주고 어떤 API는 단일 객체를 주며, 실패 응답도 상태 코드만 주는 경우와 메시지를 포함하는 경우가 섞여 있어 디코딩 로직이 화면마다 흩어졌다. 초기에는 `API 3개`를 구현하는 데 각각 평균 `2시간`이 걸렸고, 같은 방식으로 진행하면 전체가 최소 `40시간`이 필요해 일정 위험이 컸다. 또한 같은 `401`이라도 토큰 만료와 권한 부족을 구분해야 했는데, 이 분기 처리가 각 `ViewModel`에 반복되어 에러 처리 기준이 일관되지 않았다. 로그인은 Firebase로 하지만 백엔드는 자체 `JWT`를 발급하는 구조라서, Firebase 토큰으로 `Access Token`과 `Refresh Token`을 발급받고 요청마다 올바른 토큰을 헤더에 넣어야 했다. 일부 API는 리프레시 토큰을 써야 했기 때문에, 토큰 종류를 잘못 넣는 실수가 발생할 여지도 있었다.

**접근**
백엔드 팀과 협의해 모든 응답을 `ApiResponse<T>` 형태의 공통 래퍼로 통일했다. 성공 시에는 성공 여부와 데이터만 반환하고, 실패 시에는 에러 코드와 메시지를 포함하도록 규격을 맞춰 iOS의 `NetworkService`가 한 방식으로 디코딩하도록 만들었다. 디코딩 결과는 성공이면 `data`만 꺼내 반환하고, 실패면 HTTP 상태 코드와 서버 에러 코드를 함께 해석해 `NetworkError`로 매핑했다. 이 구조로 화면은 `Result<T, NetworkError>`만 받으면 되어, 화면마다 응답 형태를 맞추는 분기 코드가 사라졌다.
인증은 `RequestInterceptor` 패턴을 도입해 요청 전송 직전에 헤더를 자동 구성하도록 했다. 엔드포인트가 인증이 필요한지와 어떤 토큰을 쓰는지를 명시해 두고, 액세스 토큰은 `Authorization` 헤더에 Bearer 방식으로, 리프레시 토큰은 별도 헤더에 넣어 전송되도록 분기했다. 토큰 저장과 조회는 `TokenManager`가 `Keychain`에서 요청 직전에 읽도록 해, 갱신 이후에도 항상 최신 토큰이 적용되게 했다.

**결과**
응답 규격이 통일되면서 디코딩 실패가 눈에 띄게 감소했고, 에러 원인을 찾는 시간도 평균 `30분`에서 `5분` 수준으로 줄었다. API 하나당 구현 시간이 `2시간`에서 `20분`으로 줄어 전체 개발 기간이 단축되었고, `20개 엔드포인트`를 `1주` 안에 마무리한 뒤 UI 개선에 시간을 투자할 수 있었다. 모든 화면이 동일한 `NetworkError` 기준으로 실패를 처리하게 되어 사용자에게 보여주는 에러 메시지와 UI 분기 기준이 일관되게 유지되었다. 인증 방식이 엔드포인트 정의에 의해 자동으로 결정되면서 토큰 타입을 잘못 넣는 실수를 예방할 수 있었다.


## 02 Keychain 기반 토큰 보안 저장
UserDefaults 저장을 Keychain으로 전환해 토큰 탈취 리스크를 차단했다.

**문제**
초기에는 `Access Token`과 `Refresh Token`을 `UserDefaults`에 저장했다. 자동 로그인 기능을 테스트하는 동안에는 문제가 없어 보였고, 앱을 종료하고 다시 열어도 토큰이 유지되어 사용자가 로그인 화면을 거치지 않고 메인 화면으로 진입했다. 문제는 보안 검토 과정에서 드러났다. `UserDefaults`는 평문으로 저장되어 탈옥된 기기나 백업 파일에서 데이터를 읽을 수 있었고, `Access Token`이 노출되면 해당 사용자로 위장한 API 호출이, `Refresh Token`까지 노출되면 무한정 토큰 갱신이 가능했다. KIDK는 아동의 용돈 데이터를 다루므로 토큰 탈취는 개인정보 유출로 직결되었다.

**접근**
시스템 레벨 암호화 저장소인 `Keychain`을 도입해 토큰을 보관했다. 보안 API를 래핑한 클래스를 만들고 `Access Token`과 `Refresh Token`을 구분해 저장했으며, 저장 시도 시 이미 존재하는 항목은 자동으로 업데이트하도록 했다. 저장소 인터페이스를 분리해 테스트 환경에서는 실제 보안 저장소 대신 임시 메모리를 사용하도록 했다. 로그아웃은 두 토큰을 모두 삭제하는 단일 메서드로 구현했으며, 서버 요청 실패 여부와 관계없이 로컬 데이터는 항상 정리되도록 보장했다.

**결과**
`Keychain` 도입으로 토큰 탈취 위험이 제거되었다. `UserDefaults` 사용 시 백업 파일에서 평문 토큰을 추출할 수 있었으나, `Keychain` 적용 후 암호화된 저장소로 보호되어 동일한 공격 방법이 차단되었다. 탈옥 기기에서도 추가 공격 없이는 토큰에 접근할 수 없게 되었고, 아동 용돈 데이터를 다루는 앱의 보안 요구사항을 충족했다. 저장소 추상화를 통해 다른 민감 데이터도 동일한 보안 수준으로 보호할 수 있는 기반이 마련되었다.

## 03 Firebase-백엔드 이중 인증 흐름 통합

비동기 체이닝으로 토큰 교환 2단계 로그인 순차 처리

**문제**
`Firebase Authentication`과 백엔드 자체 `JWT`를 모두 사용하는 인증 구조에서, 사용자는 Firebase로 로그인하지만 실제 API 통신에는 백엔드가 발급한 `Access Token`과 `Refresh Token`이 필요했다. Firebase 로그인만 구현하면 백엔드 API를 호출할 수 없고, 백엔드 로그인만 구현하면 Firebase의 보안 기능을 활용할 수 없어 두 시스템을 연결하는 토큰 교환 흐름이 필요했다. 먼저 Firebase에 로그인해 `ID Token`과 `UID`를 받고, 이를 백엔드에 보내 `JWT`를 교환받은 뒤 `Keychain`에 저장하는 순차적 실행이 필요했으며, 각 단계가 실패하면 다음 단계로 진행할 수 없고 Firebase 에러인지 백엔드 에러인지 구분해 사용자에게 알려야 했다.

**접근**
Firebase의 비동기 API를 `RxSwift` 스트림으로 변환해 다른 비동기 작업과 조합할 수 있도록 했다. 로그인 성공 시 `ID Token`과 `UID`를 가져와 전달하고, 에러 발생 시 `RxSwift` 에러 처리 체인으로 전파했다. Firebase 로그인과 백엔드 로그인을 순차적으로 연결해, Firebase 로그인이 성공하면 그 결과로 백엔드 로그인을 호출하는 `2단계 흐름`을 구성했다. 백엔드 응답을 변환해 성공 시 사용자 정보를 방출하고 실패 시 에러를 전파했으며, 모든 단계가 성공하면 사용자 정보 저장과 최초 로그인 플래그 설정을 수행했다. 자동 로그인 상태는 별도 변수로 관리해 앱 실행 시 저장된 설정을 불러왔고, 로그인 성공 시 자동 로그인이 활성화되어 있으면 이메일을 저장해 다음 실행 시 입력 필드에 자동으로 채워지도록 했다.

**결과**
비동기 흐름을 순차적으로 연결하여 Firebase 로그인 결과를 기다렸다가 백엔드 로그인을 호출하는 로직을 명확하게 표현했고, 콜백 중첩 없이 가독성을 확보했다. 로그인 버튼 탭, 이메일 입력, 비밀번호 입력을 하나의 스트림으로 통합하여 처리했으며, 각 단계에서 에러 발생 시 체인이 중단되고 사용자에게 적절한 메시지를 표시했다. 저장된 이메일을 자동으로 채워줘 사용자가 비밀번호만 입력하면 되도록 했고, 두 인증 시스템을 투명하게 연결하여 사용자는 하나의 로그인 절차만 인지하게 되었다.

## 04 Vision 프레임워크 기반 영수증 OCR 자동 파싱

키워드 기반 컨텍스트 분석과 자동 입력 후 검증 워크플로우로 입력 시간 75% 단축

**문제**
아이들이 편의점에서 과자를 사고 받은 영수증의 금액을 기록할 때 매번 금액과 상호명을 직접 입력하는 것이 번거로웠고, 초등학생 사용자는 숫자 입력 실수가 많아 입력 과정이 길면 앱 사용을 포기했다. OCR로 영수증을 스캔해 자동으로 거래 내역을 생성하면 입력 시간을 줄일 수 있지만, Vision 프레임워크는 영수증이 구겨지거나 빛 반사로 일부가 안 보이는 경우 인식 정확도가 떨어졌다. 금액을 잘못 읽으면 1,000원을 10,000원으로 기록할 수 있어 아이의 잔액을 크게 왜곡하므로, OCR 결과를 어디까지 자동화하고 어디서 사용자 확인을 요구할지 설계가 필요했다.

**접근**
`Vision` 프레임워크의 텍스트 인식을 `accurate` 모드로 설정해 처리 시간이 `0.5초` 늘었지만 소수점과 쉼표 인식 정확도를 높였다. 한글과 영어를 모두 지원하도록 설정해 "CU", "합계" 같은 혼합 텍스트를 처리했다. `Document Camera`를 우선 사용해 자동으로 영수증 경계를 감지하고 조명을 보정해 배경 없이 영수증만 추출했다. 결제 금액은 "합계", "총액", "결제금액", "total" 같은 키워드를 먼저 찾고 그 주변 `3줄` 이내의 숫자를 금액으로 인식했으며, 키워드를 못 찾으면 가장 큰 숫자를 반환하는 방식으로 정확도를 `85%`에서 `95%`로 향상시켰다. 상호명은 첫 `5줄` 중 가장 긴 줄을 선택하되 `2글자` 미만이나 `30글자` 초과는 제외해 전화번호나 주소가 잘못 인식되는 것을 방지했다. OCR 결과를 입력 필드에 자동으로 채우되 편집 가능한 상태로 남겨두어 사용자가 정확하면 바로 저장하고 틀렸으면 수정 후 저장하도록 했으며, 모든 필드가 입력되어야 저장 버튼이 활성화되도록 검증 로직을 추가했다.

**결과**
평균 입력 시간이 수동 입력 `30초`에서 자동 입력 후 확인 `8초`로 `75%` 단축되었고, 오류율은 수동 입력 `5%`에서 `1%`로 감소했다. `Document Camera` 사용으로 텍스트 인식률이 `75%`에서 `95%`로 향상되었으며, 키워드 기반 파싱과 휴리스틱 조합으로 다양한 영수증 포맷에 대응했다. 자동 입력 후 확인 워크플로우로 기술의 한계를 인정하면서도 사용자 편의성을 확보했고, 불완전한 데이터가 저장되는 것을 방지해 잔액 정확성을 유지했다. 아이들이 꾸준히 거래를 기록하도록 유도해 앱 사용 지속률이 향상되었다.
