## 1) 제안 목적

KIDK City를 **“보상 연출 화면” 수준에서 끝내지 않고**, 부모 승인 → 보상 이체 → 도시 성장 반영이 끊김 없이 이어지는 **운영 가능한 제품 상태**로 완성한다.

핵심 목표:
1. 사용자 관점: 미션 보상이 도시 성장으로 즉시 체감되는 경험
2. 제품 관점: 기기별 화면 정합 + 상태 불일치 없는 안정 동기화
3. 포트폴리오 관점: 기획-구현-검증이 한 흐름으로 설명 가능한 결과물 확보

---

## 2) 현재 상태 진단 (문서 기반)

### 강점
- 기획 축이 명확함: 레벨/장소 오픈, NPC, 미션-보상 구조 정의 완료
- 핵심 도메인 구현 기반이 있음: 승인/보상/계좌 반영/도메인 이벤트 동기화 구조 확보
- SpriteKit 시티 배치 튜닝 방법론 있음: 수동 조정 + JSON 반영 협업 플랜 수립

### 미완 포인트
1. **맵 정합의 제품화 부족**
   - 튜닝 값은 방향이 있으나, "기기군 기준값 확정 + 회귀 검증" 체계 필요
2. **도시 성장 규칙의 명세화 부족**
   - 어떤 보상 이벤트가 어떤 시티 상태(게이지/레벨/건물 오픈)로 매핑되는지 규칙표 필요
3. **관측/운영 지표 부족**
   - 실제 사용자 흐름에서 어디서 이탈·실패하는지 데이터 관측 포인트 정리 필요
4. **확장 기능 경계 정리 필요**
   - 친구/팀 미션은 확장으로 두고 MVP 완성 범위를 고정해야 일정 리스크가 줄어듦

---

## 3) 완성 정의 (Definition of Done)

아래 6개가 충족되면 KIDK City를 “완성”으로 판단:

1. **정합성**: 소형/표준/대형 iPhone에서 학교/마트/홈 기준점 오차 허용범위 내
2. **연결성**: 부모 승인 성공 시 보상 이체 + 도시 UI 반영이 동일 이벤트 체인으로 완료
3. **일관성**: 앱 재실행/재로그인 후 도시 상태와 서버 상태 불일치 없음
4. **안정성**: 승인 실패/이체 실패/연출 실패 케이스별 UX 분리 대응
5. **측정성**: 미션 생성→승인→보상→도시 반영 퍼널 추적 가능
6. **설명가능성**: 포트폴리오 문서(문제-설계-결과-근거) 업데이트 완료

---

## 4) 제안 아키텍처 (완성안)

### A. City State 규격 고정
- `CityProgress` 도메인 모델 정의
  - `currentLevel`, `exp`, `unlockedZones`, `lastRewardedMissionId`, `updatedAt`
- `missionRewardCompleted` 이벤트 payload 표준화
  - `missionId`, `rewardAmount`, `rewardType`, `childId`, `timestamp`, `idempotencyKey`

### B. 보상-성장 매핑 테이블 도입
- 규칙을 코드 하드코딩이 아닌 표(또는 JSON)로 관리
- 예시:
  - 일반 미션 승인: exp +10
  - 연속 완료 보너스: exp +5
  - 목표 금액 달성형 미션: exp +20 + 배지 1
- 레벨 임계값:
  - Lv1→Lv10: 100
  - Lv10→Lv20: 250
  - Lv20→Lv30: 500

### C. 기기별 레이아웃 정합 제품화
- `xRatio/yRatio` + background display rect 계산 정책 고정
- 디버그 패널로 추출한 JSON을 `kidk_city_layout.json` 단일 소스로 관리
- `#if DEBUG` 격리 + 릴리즈 빌드 오염 방지

### D. 멀티 화면 동기화 보강
- 이벤트 수신 주체:
  - 부모 승인 목록
  - 자녀 미션 목록
  - 계좌 대시보드
  - SpriteKit City
- 실패 분기:
  - 비즈니스 실패: 재시도 CTA
  - 연출 실패: 데이터 성공 우선, UI 재렌더 트리거

## 5) 실행 로드맵 (4주, 2스프린트)

## Sprint 1 (2주): “정합 + 상태기반 완성”

### 목표
- 시티 레이아웃 안정화
- 보상 이벤트와 CityProgress 연결 완료

### 작업
1. `kidk_city_layout.json` 도입 및 scene 로더 연결
2. 디버그 조정 패널 확정(내보내기/리셋/실시간 반영)
3. `CityProgress` 모델 + 저장/로드 정책 구현
4. `missionRewardCompleted` 이벤트 payload 표준화
5. 실패 분기 UX 1차 적용(승인/이체/연출)

### 산출물
- 시티 정합 기준값 JSON v1
- 레벨/오픈 규칙표 v1
- 스모크 테스트 리포트 v1

## Sprint 2 (2주): “관측 + 포트폴리오 완성”

### 목표
- 운영 가능한 측정 체계
- 포트폴리오 설명력 강화

### 작업
1. 퍼널 이벤트 설계/적용
   - `mission_created`, `verification_submitted`, `verification_approved`, `reward_transferred`, `city_progress_updated`
2. QA 시나리오 정식화(성공/실패/복구)
3. 기기군 회귀 체크리스트 확정
4. 문서 패키지 정리
   - 구현 흐름 다이어그램
   - 상태 전이표
   - 실패/복구 정책표

### 산출물
- 계측 대시보드 기준 이벤트 목록
- QA 결과표 v1
- 최종 포트폴리오 제출 패키지

---

## 6) MVP 범위 고정 (이번 완성에 포함)

포함:
- 부모-자녀 2자 구조
- 단일 동시 미션 정책
- 미션 승인→보상 이체→도시 반영 동기화
- Lv1/Lv10/Lv20/Lv30 오픈 구조

제외(후속):
- 친구/팀 미션
- 고급 AI 추천(부모 코칭, 챗봇)
- 시즌 이벤트 확장

> 이유: 지금은 “핵심 루프 완성”이 가장 큰 가치이며, 확장은 안정 루프 위에서 진행하는 것이 비용 대비 효율이 높음.

---

## 7) 리스크 및 대응

1. **기기별 화면 편차 지속**
   - 대응: 기준 기기 3종 + 오버레이 비교 스크린샷 고정
2. **이벤트 중복 처리**
   - 대응: `idempotencyKey`로 중복 보상 방지
3. **백엔드 응답 편차**
   - 대응: 기존 fallback 파싱 유지 + 우선순위 API 표준화 병행
4. **연출 성공/데이터 실패 혼선**
   - 대응: 데이터 성공을 단일 진실로 두고 연출은 후행/복구 가능하게 분리

---

## 8) 검증 시나리오 (필수)

1. 부모 승인 성공 → 3초 내 계좌 잔액 갱신 + City 게이지 반영
2. 승인 성공 직후 앱 강제종료 후 재진입 → 상태 일치
3. 이체 실패(모의) → 사용자에게 재시도 경로 노출, 도시 반영 금지
4. 연출 실패(모의) → 데이터 성공 유지, 재렌더로 회복
5. 소형/표준/대형 기기에서 건물 클릭 hit area 정상

---

## 9) 기대 성과

- 사용자: “미션 하면 진짜 도시가 성장한다”는 체감 강화
- 제품: 상태 불일치/레이아웃 이슈로 인한 신뢰 하락 방지
- 포트폴리오: 단순 UI가 아닌 **도메인 이벤트 기반 게임형 금융 UX 완성 사례**로 차별화

---

## 10) 즉시 실행 제안 (이번 주)

1. `CityProgress` 데이터 모델 + 이벤트 payload 스키마 확정
2. `kidk_city_layout.json` 파일 분리 및 로더 연결
3. 기준 3기기 튜닝 1차(사용자 조정값 수집)
4. 승인/이체/연출 실패 분기 UI 메시지 표준화
5. 스모크 리포트 + 포트폴리오 문서 1차 업데이트

---

## 결론

KIDK City는 이미 기획과 도메인 구현의 뼈대가 충분히 갖춰져 있다. 지금 필요한 것은 기능 추가보다 **완성도 고정(정합·동기화·검증·측정)** 이다.

따라서 본 제안은
- 범위를 좁혀 핵심 루프를 완성하고,
- 기기 정합과 상태 일관성을 제품 수준으로 올린 뒤,
- 확장 기능은 다음 단계로 분리하는 전략을 권고한다.

이 경로가 가장 빠르고, 가장 설득력 있게 “완성된 KIDK City”를 만들 수 있는 방법이다.
